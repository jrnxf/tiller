# Authority and guards

This is the contract for who may do what in Tiller, and for how each rule is held: by a mechanism the model cannot talk its way past, or only by instructions and audit. It covers the role matrix, the three separate decisions (review, execute, merge), landing by the daemon after a bound approval, standing grants and away mode, the permission deny rules per role, the PreToolUse backstop, the OS sandbox, and the alternate paths T4.3 must test.

## 1. Threat model and labels

Every fleet role runs as the developer's own OS user, with the developer's `gh` login and SSH keys. No OS boundary separates the owner from an agent, so a determined process can always reach what the owner can (second opinion, point 17). The guarantee is layered defense plus audit, and this spec says plainly which layer holds each rule.

What the guards defend against, in order:

1. **Agent mistakes.** A misread brief, a stale assumption, an over-eager "I'll just merge it". This is the threat that has actually happened (Firstmate's 27 guard refusals, the cwd leak, the unsupervised subagents). Every enforced guarantee holds against it.
2. **An agent working around a refusal.** A model that retries a denied action in another form, or follows an injected instruction in fetched content. Enforced guarantees hold against every form listed in section 10. Forms not listed are named as residuals and are detected after the fact.
3. **A deliberate adversary with a shell as the developer.** Out of scope. Only detection applies (section 11).

Each guarantee in section 9 carries exactly one label:

- **Enforced**: a mechanism outside the model's control refuses the action, for the canonical form and every alternate form section 10 lists for it. The mechanism is named, and the guarantee has at least one test name. A test that drives a real `claude` session is marked `live` (section 12).
- **Convention**: only role instructions and evals hold it. Where reconcile or the audit trail catches a breach, the row names that detection and its test, but detection does not make a row enforced.

Some enforced rows depend on a host capability (the sandbox, flag-scope hooks). Those rows name the precondition. A host that fails the precondition runs that row as convention, and that fact is recorded in `docs/design/host-capabilities.md`, never discovered later. The sandbox is the exception (CP2, C19): a host where the sandbox cannot start is not cut over to Tiller until it works, so G13, G17, G20, G24 and G29's second half never run as convention on a host Tiller owns. Host B stays on Firstmate until its sandbox live tests pass.

## 3. Principals

A principal is who a mutation acts for. `tiller` resolves the principal for every call before it checks preconditions, and writes it into the event's `actor` (state.md, section 3, Event).

| Principal | Who | How `tiller` identifies it | `actor` |
|---|---|---|---|
| Owner | The developer, on the board or in a real terminal | Board: a request carrying the owner cookie (section 7). CLI: no `TILLER_SESSION_ID`, no `CLAUDECODE` in the environment, stdin is a terminal, and no Claude Code process among the caller's ancestors (the parent chain read from the OS) | `owner` (CLI, chat) or `board`; a CLI mutation carries `via_terminal` in the payload (G23) |
| Daemon | `tiller daemon`: pollers, reconcile, outbox delivery, landing | In-process; it holds the single-instance lock | `daemon` |
| Orchestrator | One live session per project | `TILLER_SESSION_ID` set at launch, resolved to a `sessions` row with `role = orchestrator` | `session:<id>` |
| Worker | A scout, builder, reviewer or verifier run | `TILLER_SESSION_ID`, resolved to a session whose run is active; the role comes from `runs.role` | `session:<id>` |
| Owner through a peer board | The developer on another host's board, acting on a record this host owns (ADR 0003) | `tiller peer serve`, started by sshd for the owner's OS user with no session id, no `CLAUDECODE` and no Claude Code ancestor, verified the frame: an unrevoked `act` row of `peer_keys`, a valid Ed25519 signature, a fresh `ts` (section 7, Peer link) | `board@<viewer label>`, with `via_peer` in the payload |
| Hook | `tiller hook <event>`, invoked by Claude Code | The harness's `session_id` in the hook payload | `hook` |
| Script | A cron or dotfiles job dropping a note (P60), or any call that matches none of the above | No session id and no terminal | `script` |
| Import | `tiller import`, run once by the owner per host | Owner CLI checks, plus the import manifest | `import` |

Rules:

- Any Claude Code session, including the developer's own interactive ones, sets `CLAUDECODE` in its shells and is the ancestor of every command it runs, so a CLI call from any agent shell is never the owner. The owner decides on the board or in a terminal they type into. Decided at CP2 (C03, amended by S05): `! tiller approve <id>` typed into the developer's own Claude session is refused (exit 6) and that is accepted; an approval given in chat goes through the orchestrator's `tiller approve --ask` route (G06), and the board and a plain terminal stay the owner surfaces. No owner token file is added. Any "one runnable command" handed to the developer (recovery.md R17, G34) is never an owner-only `tiller` command.
- Environment variables can be stripped by a shell. Stripping them turns a session into a script principal, which can do less, not more. Reaching the owner principal from an agent shell also needs a pseudo-terminal and a parent chain with no Claude Code process in it; section 10 lists the pseudo-terminal forms and the backstop denies them (G23), and the ancestry check holds the rest (section 7, "Routes and their controls").
- A session id that resolves to no row, or to an ended run, is refused for every mutation except `observation.record`.
- The owner through a peer board has exactly the board's row of the matrix, limited to the forwarding allowlist (`protocol.md` 7.4). It never has the owner CLI's extra rights: no grants, away mode, landing, spawn, host, project, config, peer or owner marker commands, and no `tiller approve --ask`, with one named exception: an unattended `peer.accept` (`tiller peer accept --unattended`), which the board host's daemon runs over ssh when the owner adds this host on that board. It needs `peer serve`'s start check (sshd for the owner, no session id, no `CLAUDECODE`, no Claude Code ancestor), and `federation.accept = false` refuses it (G45). The allowlist includes the board's ask box and Start orchestrator, so the owner can ask a peer's project and start its orchestrator, recorded as `board@<label>`; no agent can, since the fleet ask route to a peer stays off.

## 5. Three decisions: review, execute, merge

The second opinion asks that review, permission to execute and permission to merge stay separate (point 17). Each is a different record, made by a different principal, and none implies another.

| Decision | Question it answers | Who makes it | Record | What it authorizes |
|---|---|---|---|---|
| Review | Is this change good? | A reviewer or verifier run, `no-mistakes`, `/code-review`, or the owner | `reviews` row (`review.record`), bound to the commit it covered | Nothing. A pass is evidence a grant condition or the owner may weigh |
| Execute | May this work run and write? | The orchestrator (or the owner), inside capacity, the quota floor, the model rules and any away spend cap | `runs` row (`run.start`), with `config_hash` and the checked values in the event | The run's role write set (section 8): its worktree, and for a builder, pushes to the `no-mistakes` gate. Never the default branch |
| Merge | May this exact SHA reach the default branch? | The owner, or a standing grant the owner created | `approvals` row in `accepted`, bound to repo, PR, head SHA and action (or branch and head SHA for `land_direct`) | One execution of that action, by the daemon, while the binding still matches |

How the separation is held:

- `approval.decide` accepts only `decided_by = owner` or `grant:<id>`; a session caller is refused, whatever its role (G04). A review verdict, a green check or a worker's "done" never moves an approval (G27, P08).
- `review.record` with `reviewer = code-review` or `spec-review` is refused when the calling session belongs to the run being reviewed: a builder cannot review itself (G27).
- A builder's pushes reach only the `no-mistakes` gate; the backstop compares every push target with `runs.branch` (G12). A `direct-pr` builder only commits: the daemon pushes its branch and opens its PR (section 6, "Publishing a direct-pr run"). Starting a builder does not authorize landing anything.
- A grant is the owner's merge decision made in advance, with conditions. It can require a review verdict, but the review does not decide; the grant does, and its id is on the approval.

## 6. Landing

### Who lands

Only the daemon merges a PR or moves a default branch, and only by executing an `accepted` approval (plan v2, point 17). The land code lives in `crates/agents/src/land/` and every function that changes a remote takes a `DaemonLock` value. Only the daemon's single-instance lock acquisition constructs one, so no CLI path can call it (G01). `tiller land <approval>` run by the owner asks the daemon to land and waits for the result; it does not merge in its own process (`protocol.md`, section 6.4).

### The land sequence

An approval binds the head it was requested on, and the owner's accept names the head they reviewed: the board sends it, and the owner CLI refuses `tiller approve <approval>` without `--sha <head>` (a usage error, exit 2; 7 or more hex characters of the bound head match; a reject needs none). The chat route (`--ask`, G06) takes no `--sha`.

For an approval of kind `merge`:

1. The daemon takes the oldest `accepted` approval with no other approval `executing` on the same PR (the partial unique index `approvals_executing`).
2. It re-reads the PR from the forge: state, head SHA, base ref, checks, mergeable. For a grant it also re-evaluates every grant condition and checks the grant is neither revoked nor expired.
3. If the head differs from `head_sha`, or the PR is closed, the approval becomes `stale` and a `merge` attention item opens with the new SHA (state.md, `approval.execute`). While checks are `pending` the approval stays `accepted` and the daemon tries again after the next refresh. If they end in `failure`, the approval becomes `stale` and the card gets a `merge` attention item saying why. `none` passes only on a repo without CI.
4. It scrubs the PR body (P17): a quoted ask longer than 40 characters, a scrub-list term, or a stale pipeline claim refuses the land and opens an attention item (G30).
5. `approval.execute` moves it to `executing` in one transaction.
6. It merges through the forge with the bound SHA as a precondition: the forge adapter sends GitHub's merge request with `sha = head_sha` (the CLI form is `gh pr merge --match-head-commit <sha>`), so a push that lands between step 2 and step 6 makes GitHub refuse the merge with a conflict (G02).
7. `approval.finish` records `succeeded` (with the merge SHA), `failed` (with the error), or `uncertain` when the call's result could not be read. Reconcile resolves `uncertain` from the forge: a merged PR whose head was `head_sha` is `succeeded`, anything else is `failed` with a `recovery` item (T1.2).

For `land_direct` (P11, `direct-push` projects): the daemon fetches, checks the branch head equals `head_sha` and that `head_sha` descends from the remote default branch, checks the project's `checks` evidence is recorded for that SHA, then runs a plain `git push <remote> <head_sha>:refs/heads/<default>`. The remote refuses a non-fast-forward, so a moved default branch fails the land instead of overwriting it. When the project names a deploy workflow, the deploy is watched to a result that matches the pushed commit and the project's deploy environment before the card closes (state.md, section 7; protocol.md 4.6).

For `local-only` projects (P12): the same binding to branch and head SHA, merged in the project's checkout by the daemon, with no forge.

A push after approval invalidates the approval three times over: `pr.refresh` marks it `stale` when it sees the new head; step 3 refuses it; and step 6 makes the forge refuse it.

### Publishing a direct-pr run

A `direct-pr` builder only commits. It writes the PR title and body with `tiller pr describe` (`pr.describe`), and `tiller status done` is refused until it has. The daemon's publish pass, its own poller next to the land pass, then publishes every active builder run on its host whose last status is `done`, outside the sandbox and as the owner's `gh` login (`crates/agents/src/land/publish.rs`):

1. It checks the worktree has no uncommitted change to a tracked file. Untracked files are ignored: the sandbox keeps empty placeholders (`.bashrc`, `.gitconfig`, `.mcp.json` and the like) in a worker's working directory while a command runs.
2. When a PR is recorded, it reads the PR. A merged or closed PR gets no push: a run has one PR, so new work needs a new run.
3. It pushes the branch head as `<head>:refs/heads/<branch>`, never forced, and stops it after two minutes. A push of the head the remote already has changes nothing.
4. It finds the open PR on the branch, or opens one from the described title and body, links it (`pr.link`) and records the head and the PR (`publish.done`). A PR whose title or body differs from the latest description is edited to match. The worker gets a note saying what changed.

The worker writes the repository the daemon runs git in, so that git runs nothing the repository names. Every call sets `core.hooksPath=/dev/null` and `core.fsmonitor=false`, and the fetch, the descent check, the status check, the push and the local fast-forward run in a clean room: a temporary bare git dir that borrows the repository's objects through `objects/info/alternates` and never reads its config. A filter driver, `core.sshCommand`, `remote.<name>.uploadpack`, credential helper or `url.*.insteadOf` written to the repository's config therefore never runs as the owner. The fetch and push URL is still the project remote's configured URL; one that names a transport helper (`ext::`, `fd::`) or reads as an option is refused.

The record makes it idempotent. A run is left alone while its record is current: the head is pushed, the PR is recorded, nothing failed since, and neither a new description nor a new `done` came after the push. Every later `done` publishes again: a new head is pushed to the same PR, a new description becomes its title and body, and an unchanged run is told it is up to date. The forge is asked for an open PR on the branch before one is opened, so a crash between the open and the record finds that PR instead of opening a second. A failure is recorded (`publish.failed`) and raised as a `recovery` attention item carrying the real error, and sent to the worker. A run has one open item per head and step: a repeat raises nothing new while it is open, and a new one once the owner has closed it. The pass tries again at once for a new head or a new `done`, and after 15 minutes otherwise; a later success withdraws the item.

### Enforced merge gate (CP2, S03)

On a project that promises a mandatory merge gate, the forge itself refuses every merge and default-branch update that does not come from the daemon. Detection after the fact (G10's old form) cannot keep that promise, so it is now a labelled fallback, not the default.

- **Which projects.** Every project with `delivery` `no-mistakes` or `no-mistakes-prod-only` is gated. Any other project with a forge repo may opt in the same way: a `direct-pr` project, or a `direct-push` project, whose land push then goes through the App because the ruleset refuses every other pusher. The ruleset is the opt-in: the check runs on every live project with a forge repo and delivery other than `local-only`, and a project whose repo has no matching ruleset stays `detect` without an event or an item.
- **The identity.** One GitHub App, owned by the owner's account (for example `tiller-merge`), installed on each gated repo. Its permissions are the minimum the land sequence needs (contents, pull requests and workflows write, checks and metadata read; workflows because a land may change `.github/workflows/`). The daemon's forge adapter mints a short-lived installation token for each land and uses it only for the merge call (step 6) and, on an opted-in `direct-push` project, the default-branch push. Every other forge call keeps using the owner's `gh-axi` login.
- **The key.** The App's private key is stored under `~/.tiller/forge-app/` (the Tiller home's `forge-app/`): `private-key.pem`, as GitHub downloads it, with mode 600 (a key readable by group or others is refused), beside `app-id`, the App's numeric id. The daemon reads both on each use, signs a short-lived App JWT (RS256) and mints an installation token scoped to the one repo; with no key file it has no App. Every fleet role is denied the directory for read and write by the deny rules and the sandbox (G20), and no rendered prompt, command output or log line ever contains. Workers never hold a token that can merge: their `gh` login is the owner's account, which the ruleset does not let through.
- **The ruleset.** One branch ruleset per gated repo on the default branch: require a pull request, require the project's status checks, restrict updates, block force pushes and deletion, with the App as the only bypass actor. The owner's own account is deliberately not a bypass actor, because workers use the owner's login; the owner merges a gated project through Tiller (the board or `tiller approve` in a terminal), and an emergency hand merge means editing the ruleset by hand, which reconcile then reports like any outside merge (recovery.md R07).
- **`projects.merge_gate`.** `enforced` or `detect`. `enforced` is recorded only after the daemon's ruleset check passes: it reads the repo's rulesets through the API and confirms the rules above with the App as the only bypass actor. The check runs within a minute of `tiller project add`, once an hour after that, and again within a minute of the App's files changing; it writes through `project.merge_gate` (state.md, section 8). The rules are read as the owner's `gh` login, which as the repo's admin sees the bypass list; a read that fails changes nothing. `tiller doctor` reports the stored value, its last change, and whether the App key is usable. The owner's setup steps are in `docs/plan/merge-app-setup.md`. A check that later fails (the ruleset was edited or removed) moves the project to `detect` with a `host.degraded` event and a `recovery` item on `fleet-1`, never silently.
- **The fallback.** `detect` is the explicitly labelled fallback mode, kept only until the App exists for that repo: the board shows "merge gate: detection only" on the project, `tiller doctor` lists it, and G10 runs as convention plus detection there. Creating the App and installing it per repo is a one-time owner setup step on the cutover checklist (`docs/plan/checklist.md`, Cutover).

### Merge on the owner's word in chat

P12 lands a PR on the developer's word, and the developer often gives it in chat. The orchestrator records it with `tiller approve <approval> --ask <ask id>`. `tiller` accepts this only when:

- the caller is the live orchestrator of the approval's project;
- the ask has `source = prompt`, was recorded by the `UserPromptSubmit` hook in that orchestrator's session, and has `received_at` after the approval's `requested_at`;
- the approval is `requested` and its binding still matches the cache.

The decision is recorded with `decided_by = owner`, `answered_via = chat`, and the ask id in the event payload. The board's receipt quotes the ask's text beside the approval. What `tiller` can check is the binding and the provenance of the ask (G06). Whether the words meant "merge this" is the orchestrator's reading, so that part is convention (G07), and the quoted receipt is how the owner catches a misreading.

### Standing grants (P13)

A grant is the owner's merge decision for a class of PRs, made in advance. Only the owner creates or revokes one (`grant.create`, `grant.revoke`), on the board or in a terminal. A fleet role may recommend one in a `decision` attention item; it can never create one (G04).

`grants.conditions` is JSON, version 1. Every listed condition must hold, at match time and again at execution:

```json
{
  "v": 1,
  "actions": ["squash"],
  "base_ref": "main",
  "head_ref_pattern": "fm/*",
  "opened_by_fleet_run": true,
  "card_kinds": ["ship"],
  "checks": "success",
  "pipeline": "passed",
  "reviews": { "require": ["code-review"], "max_high": 0 },
  "exclude_paths": [".github/workflows/**"],
  "expires_at": null,
  "away_approval_id": null
}
```

- `actions`: the merge actions the grant may choose; the approval records the one used. `base_ref`: the PR must target this branch. `head_ref_pattern`: a glob on the PR's head branch, or null.
- `opened_by_fleet_run`: the PR's `prs.run_id` is set and belongs to a card of this project. This is what "in scope" means in P13.
- `checks`: required `prs.checks`. `pipeline`: required `prs.pipeline_state`, or null for projects without `no-mistakes`. While the PR's project is `pre-launch`, the matcher skips the `pipeline` condition for a PR with no pipeline run (a pipeline that ran and failed still blocks) and enforces it again from the moment of launch; every other condition still applies (`docs/design/pre-launch-validation.md`, D4).
- `reviews`: required reviewer kinds with a `pass` verdict on the PR's run, and the most high findings allowed, or null. A review counts only when its `head_sha` equals the PR head the grant would accept, and the newest review of each kind at that head decides. A push after a review therefore needs a new review before a grant accepts the new head. A review with no recorded SHA (a row from before migration 16) never satisfies the condition; it stays evidence for the owner.
- `exclude_paths`: globs; a PR touching any matching path never matches the grant and goes to the owner. Every source-map path (`memory.md` section 3) is excluded from every grant whatever `exclude_paths` says, so a PR that changes what a fleet role loads always reaches the owner as a memory change (CP2, S01: there is no standing memory grant).
- `expires_at`: UTC timestamp, or null for a standing grant. `away_approval_id`: set on a grant created by away mode (below).

`grant.create` checks this shape wherever the grant comes from: the owner CLI, the board's API or away mode. It refuses a key version 1 does not have, a value of the wrong type, and a value outside its set (an unknown action, card kind, checks or pipeline state, or reviewer kind), text with a space at either end (it could never match a branch or a path), and a `pipeline` on a `land_direct` grant, with a `usage` error that names the key. A key that is absent or null does not limit the grant, except `opened_by_fleet_run` and `exclude_paths`: the land sequence reads them as true or false and as a list, so a null there is refused and the key is left out instead. An empty `exclude_paths` list is allowed and means no extra paths. `away.start` and `away.edit` check a `merge` conditions object the same way before the window opens, and name it as the away merge in the error. The matcher still reads the stored JSON as it is, so a grant made before this check keeps working.

A project with no grant waits for the owner's word on every merge; that is how "a few projects always wait" (P13) is expressed. A grant of kind `land_direct` uses the same shape, with `actions = ["push"]`, the condition `checks` meaning the project's recorded checks, and no `pipeline`.

The daemon matches grants when a PR becomes eligible (checks done, no open approval). A match creates the approval already `accepted`, with `decided_by = grant:<id>` and bound to the head SHA at that moment, so the audit trail matches a hand approval (state.md, Approval). A revoked or expired grant matches nothing, and an `accepted` approval whose grant was revoked before execution becomes `stale` (G05).

### Away mode (P34)

`away.start`, owner only, writes one `approvals` row of kind `away`, decided by the owner when it is created, with `scope`:

```json
{
  "v": 1,
  "until_at": "2026-11-07T18:00:00.000Z",
  "orders": "keep going on alpha-42 and alpha-43; hold anything that changes the schema",
  "projects": ["alpha"],
  "spend": { "max_new_runs": 6, "quota_floor_percent": 20 },
  "merge": "grants"
}
```

- `orders` is text the orchestrators read. Following it is convention.
- `spend` is enforced by `tiller spawn` while the contract is active (G28): no run starts beyond `max_new_runs`, or below `quota_floor_percent` when that is stricter than the standing floor.
- `merge` is `none` (no merges while away, even under existing grants), `grants` (existing grants only), or a grant conditions object: then `away.start` also creates a temporary grant per listed project with `expires_at = until_at` and `away_approval_id` set.
- Away can narrow authority or add temporary grants the owner wrote into the scope. It never answers attention items or decides pending approvals.

`away.edit`, owner only, replaces the scope of the running contract in place. The window start and the run count carry on, the temporary grants of the old scope are revoked and the new scope's are created. It is refused when away mode is not on.

`away.end` (the owner returns, or `until_at` passes and reconcile ends it) revokes the temporary grants and moves the approval to `succeeded`. The return brief (T4.5) is read from the records for the contract's window, so it is the same whenever it is asked: `tiller away brief`, and the output of `tiller away end`. It lists the orders, the spend against the cap, the runs that started, the cards that landed, the merges a grant made, and the attention items and approvals still waiting for the owner.

## 7. Guard layers

From the outside in. A guarantee in section 9 names the layers that hold it.

1. **Launch form** (T4.2). Every fleet role starts as:

   `claude --append-system-prompt-file <role>.md --settings <run fragment> --permission-mode <mode> --strict-mcp-config --mcp-config <role mcp>`

   with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `TILLER_SESSION_ID`, `TILLER_RUN_ID` and `TILLER_ROLE` in the environment, Remote Control off for workers (P68), no `--plugin-dir`, and no mods. Workers run in `dontAsk` (decided at CP2, C17: an action outside a worker's allow rules is denied, never left waiting on a dialog nobody watches, so the board's permission-prompt section serves only the orchestrator); the orchestrator runs in `auto` mode (decided after CP5, on the owner's word: the owner is present but wants a hands-off orchestrator, and the default mode stopped it on a harmless compound read-only command that a `Bash(tiller *)` allow rule does not match). Deny rules (evaluated first, in every mode), the backstop hook and the sandbox stay the hard limits; Claude Code's classifier decides only what they leave open. The orchestrator fragment sets `defaultMode: "auto"` and every launch, resume and relaunch passes `--permission-mode auto`. If this Claude Code does not offer auto mode, spawn falls back to `default` and says so in its output; it never falls back to `bypassPermissions` or `dontAsk`. Nobody runs in `bypassPermissions`.

   Before the launch line is written, for the orchestrator and for workers alike, at first launch, resume and relaunch, tiller records Claude Code's workspace trust for the launch directory: `hasTrustDialogAccepted: true` under `projects["<absolute path>"]` in `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`, and on the primary checkout's entry too when the directory is a linked worktree. No session then stops at the trust dialog, and nothing is typed to answer it (G29). The write sets only that flag: every other key is kept byte for byte, the external-imports consent is never written, the write holds the same lock Claude Code's writers take on the file (`.claude.json.lock`), and the new file replaces the old by an atomic rename. A store that is not valid JSON, or whose `projects` or entry is not an object, is never overwritten; the launch is refused with an error that names the file, as it is whenever the flag cannot be recorded. When tiller's own environment sets `CLAUDE_CONFIG_DIR`, the launch line carries it; when it does not, the launch line unsets any the pane inherited. Either way the session reads the config tiller wrote. An older install's `.config.json`, while Claude Code still reads it, is the file written.
2. **Run fragment.** `tiller spawn` generates the settings fragment per run from the role template in `roles/` (T4.1), with absolute paths for the worktree, the scratch directory and the protected roots filled in. Its SHA-256 goes into `config_hash`. It carries the deny and allow rules (section 8), the PreToolUse hook, and the sandbox settings. It is passed with `--settings`, never written to the project's tracked `.claude/settings.json`: tracked project settings follow the repo into every worktree and would disarm or over-arm other sessions (Firstmate's subagent-guard learned this). If T4.3 finds flag-scope PreToolUse does not fire on a host, the fallback is the worktree's untracked `.claude/settings.local.json`, written by spawn.
3. **Permission rules.** Deny rules per role, plus `dontAsk` with narrow allow rules for workers. They are cheap, apply in every mode, and catch the canonical forms.
4. **PreToolUse backstop** (section 9's mechanism for alternate forms). One decision owner, `tiller guard pretool`, sees every tool call of every fleet role.
5. **OS sandbox.** For every fleet role: `sandbox.enabled`, `failIfUnavailable: true`, `allowUnsandboxedCommands: false`. Write set: the role's write set from section 8. `denyRead` and `denyWrite` on the Tiller home (`<tiller_home>`: `TILLER_HOME` when set, else `~/.tiller`) and the secret patterns. Every launch also exports `TILLER_HOME`, so the session's `tiller` and its backstop hook find that same home. Network: an allow list per project (the forge, the package registries its checks need); no localhost. Unix sockets: only the `no-mistakes` daemon socket. `excludedCommands` names only the packaged `tiller` binary by its absolute Nix-store path, so `tiller` reaches `state.db`, and `tiller` checks its own caller (layer 6). Roles type bare `tiller`; the backstop (layer 4) writes the packaged path in for a lone call, with every argument quoted. Why this one exception is safe, and what it does not cover, is "Routes and their controls" below.
6. **`tiller` self-checks.** Every mutation resolves its principal (section 3) and checks the role matrix (section 4) inside its transaction, before its preconditions. Owner-only commands refuse any call that is not the owner principal. This layer holds whatever the harness does.
7. **Forge and git preconditions.** The merge carries the bound SHA; a default-branch push is fast-forward only.
8. **Detection.** Reconcile and the audit trail (section 11). Detection never makes a row enforced, but it bounds how long a breach stays unseen: one reconcile cycle.

### Board API credential

The board's mutations need the owner principal. The daemon serves reads to any request with a local `Host` header; at an owner-allowed `Host` it serves reads only with the owner cookie, and without it nothing but the signed-out screen and the sign-in itself. It accepts a mutation only with all of:

- the owner cookie: `HttpOnly`, `SameSite=Strict` (and `Secure` when minted at an allowed host), minted when the owner runs `tiller board --login` in a terminal, which prints a one-time login link and an 8-digit code that work once, together, and for one minute (owner CLI checks apply). The limits on codes count per client address, so a stranger guessing at a public board spends only its own tries: three wrong codes from one client, or ten from one IPv6 /48, burn the code for that client or network only, and each client may try at most 10 codes a minute (an IPv6 network 30). A code burns for everyone only on the 1000th wrong code from all clients together, which caps a guesser's chance at 1 in 100,000 a code and takes 334 IPv4 addresses or 100 IPv6 networks guessing within its minute (`protocol.md` 7.1). The code is never logged. It survives daemon restarts and expires 30 days after it was minted (decided at CP2, C15), after which the owner runs `tiller board --login` again. Sign out on the board ends it on the daemon at once;
- a `Host` of `127.0.0.1:<port>` or `localhost:<port>`, which stops DNS rebinding, or exactly a name the owner allowed with `tiller daemon --allow-host`: a TLS-terminating reverse proxy's name, which only the owner can add;
- the board's own `Origin` for that `Host`: `http://` on loopback, `https://` at an allowed name, so a page served over plain http there can never write;
- the record's `rev` or the transition's preconditions (state.md, section 1).

The terminal mirror (an agent's live pane and its scrollback, the owner's keys into it, the Fit that sizes the pane to the board while it shows, and the read-only tail of a pane on a saved machine) needs the same, though watching writes nothing: a pane can show anything the agent read, and a key typed there acts as the agent. At an `--allow-host` name it is served on the same terms as every mutation there, and its keys and Fit reach panes on this machine only; a pane on a saved machine is read through herdr, never typed into (saved machines go at the cutover [H]). A pane on a paired peer host is watched read-only: the board host relays the stream from the owning host over a pane link (`protocol.md` 10.7), on the same terms as a local mirror, and its keys, Fit, tail, prompt and answer stay refused with a reason. No path types into a peer pane.

The cookie's hash is stored under `~/.tiller`, which every fleet role is denied (G20). Sandboxed roles cannot reach localhost at all (G24). T1.3 owns the endpoint list; this spec owns the requirement.

### Peer link (ADR 0003)

The one route by which another host changes this host's records. It is the owner's, and it is held at both ends:

- **Board host.** A forwarded mutation passes the board credential above first. The private key is `~/.tiller/peers/<label>.key` (mode 0600), under `~/.tiller`, which every fleet role is denied (G20); only the daemon reads it, to sign. The daemon opens the link itself; no command exposes a signing operation, so nothing else on the host can get a frame signed.
- **Transport.** The owner's SSH, with host-key checking and `BatchMode`. No new listening port. The owner cookie never crosses hosts.
- **Peer.** `tiller peer serve` refuses to start unless sshd started it for the owner (`SSH_CONNECTION` set, no `TILLER_SESSION_ID`, no `CLAUDECODE`, no Claude Code ancestor). It answers a `hello` only for an unrevoked `peer_keys` row while config `federation.accept` is not `false`, and checks a `mutate` in the one order `protocol.md` 10.3 step 3 gives: `federation.accept`, an unrevoked key row, its signature, `ts` within 120 s, this host's `host_id`, scope `act`, the allowlist, the owner marker (G26) and a project this host owns (G25). Then the same core function runs with its own preconditions.
- **Pairing.** Two routes, both the owner's. `tiller peer add` needs the owner CLI principal on the board host (G22), and its `peer.accept` needs the owner principal on the peer (a terminal from `ssh -t`, no Claude ancestor). The board's Add a host (`POST /api/v1/peers`) needs the board credential above, is never forwarded, and runs the peer's `tiller peer accept --unattended` over `ssh -T` in `BatchMode` with the default host key check; that accept needs `peer serve`'s start check instead of a terminal, and its `peer.accepted` event carries `unattended: true` with actor `board@<label>`, so the peer's audit shows every pairing no terminal saw. Either way a fleet role cannot add a key. Config `federation.accept = false` refuses every pairing, both routes alike, every `hello`, and every `mutate` and `query` on a link already open. Cutting a link is the owner's too: the board's Unpair (`DELETE /api/v1/peers/{label}`) and Revoke key (`DELETE /api/v1/peer-keys/{id}`) need the board credential, are never forwarded, and run the code `tiller peer remove` and `tiller peer revoke` run. The private key never leaves `~/.tiller/peers/`: no response, event or log carries it (G45).
- **Out of scope.** Whoever can read the board host's `~/.tiller` can act as the owner on every `act` peer. That is the owner's own shell, the adversary section 1 leaves out. A `--read-only` pairing and a host that sets `federation.accept = false` bound the reach.

### Routes and their controls (CP2, S05)

Claude Code's sandbox covers the shell only. Each other route a fleet role has into the host needs its own control, and the one sandbox exception, `tiller`, is safe only if it can do no more than the caller's row in the role matrix. This table is the evidence for C20 (keep `tiller` as the one excluded command) and for the owner principal (C03).

| Route | What runs there | Control | What exempt `tiller` can do from it | How the receiver identifies the caller | Host precondition (H01) |
|---|---|---|---|---|---|
| Shell: the Bash tool and every child process | the role's commands, scripts and interpreters | the sandbox (write set, `denyRead`, network allow list, socket list, `allowUnsandboxedCommands: false`); deny rules; the backstop | only the packaged `tiller` binary, named by its absolute path, leaves the sandbox; the backstop writes that path in for a lone bare `tiller` ("How roles reach the exempt binary" below). It reaches `state.db` and writes exactly what the caller's matrix row allows, checked inside its own transaction (layer 6). A process the role detaches (`setsid`, double fork) loses the Claude Code ancestor but stays inside the sandbox, where `~/.tiller` is unreadable, so it cannot use `tiller` at all | `tiller` resolves the principal from `TILLER_SESSION_ID` (a `sessions` row), `CLAUDECODE`, a terminal on stdin, and its parent chain: a Claude Code process among its ancestors makes it never the owner, whatever the environment says | the sandbox starts (C19: no cutover without it); flag-scope hooks for the backstop |
| File tools: `Read`, `Edit`, `Write`, `NotebookEdit` | inside the Claude Code process, outside the sandbox | deny rules (evaluated first, in every mode); `dontAsk` with `Edit` allowed only in the write set (workers); the backstop | none: file tools cannot run a program | not applicable: the permission engine reads the session's own fragment | none for deny rules; the backstop needs hooks |

What this shows, and the CP2 decision on open item 4 (C20, amended by S05): `tiller` stays the one excluded command. The exemption gives a fleet role no right its matrix row lacks, because authority is checked inside `tiller` and the daemon takes no calls, only rows. Two conditions are not yet proven and T4.3 tests both on every host before C20 counts: the exclusion applies only to the packaged binary as a simple command (section 2; the backstop also denies, as `[guard-tamper]`, any command that assigns `PATH`, defines a function or alias named `tiller`, or runs a `tiller` that resolves anywhere but the packaged path), and the ancestry check finds the Claude Code process on each host (`core::authority::owner_check_refuses_claude_ancestor`). If either fails, the alternative (every agent process inside the sandbox, `tiller` reaching the daemon over a socket that identifies its peer) comes back to the owner as a stop-and-ask.

**How roles reach the exempt binary** (Wednesday 2026-11-04). Role prompts, allow rules and the owner type bare `tiller`, but the exclusion names the absolute path and Claude Code matches it against the command text (section 2). So a bare `tiller` ran inside the sandbox, where `~/.tiller` is unreadable, and every state command failed. Two fixes were weighed:

- **Exempt the bare name, with a `PATH` guarantee.** Rejected. The exemption would follow the name, and the name is resolved by the Bash tool's shell at run time, not by the launch: that shell loads the owner's shell snapshot and starts `PATH` with Claude Code's own directories (section 2). Any `tiller` function, alias or `PATH` entry that shell picks up, today or after a dotfiles change, would run outside the sandbox with the role's code in it. That is the whole sandbox, not one binary, so a single miss in the guarantee is a full escape.
- **Keep the absolute exemption and rewrite the call (chosen).** `tiller guard pretool` answers an allowed call whose whole command is one top-level simple command, its first word the literal unquoted `tiller`, every word static, with no assignment and no redirection, with `updatedInput`: the packaged path, which is the guard's own executable and the path spawn rendered into the fragment (the stable path: the link the binary was invoked through, such as the profile's `tiller`, when it resolves to the running file, else a profile link that does, else the file itself; so a release moves the link and an open session's hooks run the new binary, and the guard still compares paths by their canonical form), followed by each argument in single quotes (a leading `~` or `~/` stays bare so it still expands). The quotes matter because the call leaves the sandbox: the Bash tool's zsh expands a global alias or an `=word` in any unquoted argument (section 2), so an owner's `alias -g G='| grep'` would turn `tiller card list G token` into a pipe that runs `grep` unsandboxed. A lone call that already names the packaged path is requoted the same way. Spawn refuses a `<tiller>` that is not a plain word (letters, digits and `/._+-@,:%=`), so the rewrite is never silently skipped. Claude Code then runs the permission rules and the exclusion on that text (section 2), so every `Bash(tiller ...)` deny rule also has its `Bash(<tiller> ...)` form and the orchestrator's allow is `Bash(<tiller> *)` (section 8). The exception stays one absolute path, unchanged.

The rewritten command is one the role could type itself, so the rewrite grants nothing new. Quoting does change which deny rules match: Claude Code compares the text, so `Bash(<tiller> approve *)` does not match `<tiller> 'approve' ...` (section 2). That is no loss, since a role could always type the quotes itself; the backstop has already judged the call on its parsed words before rewriting it, and `tiller` checks its caller (layer 6). Nothing but the packaged file runs outside the sandbox: an absolute path is never looked up on `PATH`, and a function or alias named by the path (zsh expands both, bash the function) would have to be defined in the same command, since a role cannot write the shell snapshot under `~/.claude` and functions do not outlive a Bash call. That makes it a list, which runs sandboxed, and the backstop denies it `[guard-tamper]`, as it denies a `tiller` function, alias or `PATH` change. What a shadowed `tiller` can and cannot do:

- A lone bare `tiller` is never looked up: the backstop replaces it, so a role-written `./tiller`, a `PATH` entry, a function or an alias in the snapshot never runs from it.
- Any other form (after `cd`, in a pipe, after `&&`, with an assignment, a redirection or an expansion) is not rewritten and runs sandboxed. A shadowed `tiller` there is just the role's own code under the role's own sandbox: it cannot read or write `~/.tiller`, leave the write set or reach localhost. The packaged binary in such a form is sandboxed too and is refused with a hint to run it on its own, typed as the packaged path (`cli::commands::a_session_that_cannot_see_state_db_is_told_it_ran_sandboxed`).
- The binary that does leave the sandbox is the packaged one, and it still checks its caller (layer 6): a fleet session resolves to its `sessions` row, never to the owner, and gets only its matrix row.

If hooks do not fire, nothing is rewritten and a bare `tiller` fails closed inside the sandbox. The curator launches with no hooks (`learning-loop.md` section 4), so its prompt and its allow rules name the packaged path itself. Tests: `agents::guards::bare_tiller_is_rewritten_to_the_packaged_path`, `agents::guards::rewrite_quotes_words_zsh_would_expand`, `agents::guards::a_lone_packaged_call_is_requoted`, `agents::guards::only_a_lone_literal_tiller_is_rewritten`, `agents::roles::tests::render_refuses_an_empty_relative_or_slashed_path`, `agents::guards::tiller_rules_name_both_forms`, `cli::guard::bare_tiller_is_rewritten_to_the_running_binary`, and live `agents::guards::live::bare_tiller_reads_the_record_the_sandbox_hides` (a lone bare `tiller` reads the record while `head` of `state.db` and the packaged binary after `&&` cannot).

### Roles on other harnesses (D04 kept)

The policy has one owner, `tiller guard`, and each harness adapter only carries its tool calls to it, as Firstmate's guards did. `tiller spawn` refuses to launch a role on a harness whose adapter does not provide both a pre-tool hook transport and an equivalent of the sandbox (G35), so every enforced row stays true on every harness Tiller launches. Claude Code is the only adapter at day one.

## 9. Guarantees

The PreToolUse backstop is the mechanism behind most rows, so it is specified first.

### The PreToolUse backstop

- **Owner.** `tiller guard pretool --role <role>` (`crates/agents/src/guards/`). It reads the hook payload on stdin, resolves the session to its run, and decides. It never runs, expands or sources any byte of the command.
- **Matcher.** Every tool name (`.*`), so a tool added by a future Claude Code version reaches the classifier (Firstmate's subagent-guard rule). MCP tools are classified too: a `mcp__` tool whose name contains `merge`, `push`, `delete`, `create_ref` or `update_ref` is denied to every fleet role, and fleet roles launch with `--strict-mcp-config` and no GitHub MCP server in the first place.
- **Shell classification.** One shell lexer splits the command into its command positions, including the command strings of the shells (`sh`, `bash`, `zsh`, `dash`, `ksh`, `mksh`, `ash`, `tcsh`, `csh` with `-c`, `fish` with `-c` or `--init-command`, and `pwsh` with `-Command`, `-CommandWithArgs` or `-EncodedCommand`), a script that a shell, `sudo -s`, `sudo -i`, `doas -s` or `su` reads on standard input, and `eval` payloads, subshells, command substitutions, pipelines, and lists. It strips wrappers (`env`, `command`, `builtin`, `busybox`, `exec`, `xargs`, `sudo`, `doas`, `sudoedit`, `su`, `nix develop` and `nix shell` after `-c` or `--command`, `nix-shell` after `--run` or `--command`, `direnv exec`, `watch`, and the command runners `strace`, `ltrace`, `nice`, `ionice`, `timeout`, `nohup`, `chrt`, `taskset`, `setsid`, `stdbuf`, `unshare`, `nsenter`, `setpriv`, `runuser`, `chroot`, `fakeroot`, `flock`, `time`, `caffeinate`, `systemd-inhibit`) and leading assignments. It reads the options of `env`, `exec`, `sudo`, `doas`, `su`, `xargs`, `fish`, `pwsh`, `watch` and the runners as the program does (bundled short options, attached or detached values, long options and their unique prefixes, `--`, and the `env -S` string read again as `env` arguments), so every spelling of an environment-clearing option is `[identity]`. `sudo -l`, `-V`, `-v`, `-K` and `--help`, and `doas -C` and `-L`, run no command and are allowed. `sudoedit` and `sudo -e` run no command either, and the guard checks their file arguments against the write rules. `xargs` runs its command with the words it reads appended, unless `-I` or `-J` places them, so a tiller word that depends on its input is unseen. `watch` without `-x` in its options is read as one command string. `nix` takes every setting as a flag, so the guard cannot name all its flags. Every word that may be `-c` or `--command` starts a reading of the command: after any flag, before or after the subcommand, and in a short cluster. The guard splits nix's words the way nix does: one flag per letter, and the rest from the first character that is not a letter as one more word, which nix splits again when it reads it as a flag (`-Lc`, `-L-c`, `-c/path`). The guard knows how many values the common flags take, and a `--no-NAME` setting takes none, so a `-c` that is a flag's value (`-k -c`, `--arg x -c`) is not the command. A `-c` after a flag it does not know may be that flag's value, so the words after it are still read as nix's flags, and a known flag among them may be a value too. The first `-c` that is surely the flag ends nix's words, and so does `--`. `nix run` runs a program not known before it runs, with the words after `--`, so it is handled like any program not known before it runs. nix 2.3 `nix run` takes `-c` and `-i` like `nix shell`, and the guard reads it the same way. A word not known before it runs may be any flag, `develop` among them, so it is handled by the fail mode below. `nix develop` (or `dev-shell`) and `nix shell` with no `-c` that is surely the flag start a shell that reads standard input, and so does `nix-shell` with neither `--run` nor `--command`. `nix-shell` runs its last string, so the guard checks every `--run` and `--command` string, and standard input too. A `nix-shell` word not known before it runs may be `--pure`, so it is handled by the fail mode below. `nix develop -i`, `nix shell --ignore-env` (or `--ignore-environment`) and `nix-shell --pure` clear the environment and are `[identity]`. `-u` (`--unset-env-var`, `--unset`) and `-s` (`--set-env-var`) follow the rules of `env`. The words of `nix` before its command keep the write rules (`--profile`, `--out-link`). `direnv exec PATH` runs PATH itself when it is a file, so the command is read at both places, unless PATH is made only of `.`, `..` and `/`. direnv drops a trailing `/` before it looks at PATH, so `tiller/` may still run `tiller`. A `direnv` subcommand not known before it runs is handled by the fail mode below. A wrapper option it cannot read is handled by the fail mode below. It normalizes path-qualified programs (`/usr/bin/git` is `git`). For `git` it skips global options (`-C <dir>`, `-c <k=v>`, `--git-dir`, `--work-tree`) to find the subcommand, and for `push` it parses refspecs, `+` prefixes, `--force*`, `--mirror`, `--all`, `--delete` and `:<ref>` deletion forms.
- **Decisions.** Per role, the backstop denies:
  - every protected command named in section 8 in any of these forms;
  - a `git push` whose destination ref is the default branch, any ref other than the run's `runs.branch`, or the gate remote for a non-builder;
  - `gh` or `gh-axi` calls that merge, update a ref, delete a branch (a word not known before it runs counts as the flag past the positional arguments the subcommand takes, so `gh pr close $PR` is allowed and `gh pr close 5 $FLAG` is not), approve a PR, retarget a PR at the default branch, delete a release, or call the raw API (`api`, `graphql`) with a write method or a mutation;
  - any HTTP client binary (`curl`, `wget`, `http`, `xh`, `aria2c`, `nc`);
  - `env -u` or `unset` of `TILLER_*` or `CLAUDECODE`, and pseudo-terminal allocators (`script`, `expect`, `unbuffer`, `socat ... pty`);
  - writes into `~/.tiller`, `~/.claude`, `.claude/` or `.git/hooks`, and `git config` that sets `core.hooksPath`;
  - an owner-only `tiller` command (`[owner-only]`): `approve` (except the orchestrator's one chat form, section 8), `grant`, `away`, `land`, `board`, `import`, `hook`, `guard`, `owner`, `init`, `backup`, `export`, `restore`, `daemon`, `host`, every `retro` command, every `learn` command except a bare `learn`, `learn gate` and `learn config`, a bare `project` and `project` with any word but `list`, `migrate down`, `config set`, `mem approve`, and `agent restart` and `agent focus`. A word the guard cannot read counts as unseen. An unseen first word after `tiller` is owner-only. An unseen second word is owner-only for `migrate`, `config`, `mem`, `learn` and `agent`, as is a second word that `xargs` appends (`tiller agent "$SUB" alpha-1`, `xargs tiller migrate`). The curator launches with no hooks, so this list does not bind its `tiller retro finish`;
  - `ssh`, `mosh` or `et` whose remote command names `tiller`, and any `tiller peer` form (`[peer]`, ADR 0003);
  - for the orchestrator, a top-level `cd`, `pushd` or `popd` that persists into a project checkout or worktree (Firstmate's cd guard), and any delegation-shaped tool name (Firstmate's subagent-guard stems, with its observe-only and plan-only exceptions).
- **Fail mode.** A command that contains no protected token after quote removal is allowed fast, without a database read. A command that contains one but cannot be classified (malformed syntax, an unknown decoder form) is **denied**: fail closed on protected commands, as Firstmate's arm guard does, because a wrong allow here is a merge or a lost worktree. If the guard binary is missing or crashes, Claude Code treats the hook as a non-blocking error; the deny rules and the sandbox still hold, and G35 makes sure a session never starts in that state.
- **Output.** A deny carries one stable code in brackets (`[merge]`, `[default-push]`, `[foreign-branch]`, `[http-client]`, `[owner-only]`, `[identity]`, `[state-write]`, `[guard-tamper]`, `[worktree-admin]`, `[delegation]`, `[persistent-cd]`, `[peer]`) and one sentence that names the allowed path ("ask the orchestrator to request a merge approval"). T4.3 pins the exact transport against the installed CLI version, as Firstmate's cd guard documents: exit code 2, the decision JSON (`hookSpecificOutput` with `permissionDecision: "deny"` and the reason) on stderr, and nothing on stdout (`cli::guard::deny_exits_two_with_the_decision_on_stderr`; live `agents::guards::live::backstop_deny_reaches_the_model`). An allow exits 0 and prints nothing, except for a lone `tiller` call, which exits 0 with `updatedInput` on stdout: the packaged path and each argument quoted (section 7, "How roles reach the exempt binary"; `cli::guard::bare_tiller_is_rewritten_to_the_running_binary`). Because Claude Code reads exit 2 as a deny, a `tiller guard` or `tiller hook` command line that does not parse (a broken fragment) exits 0 silently, like an unknown role: the deny rules and the sandbox still hold, and spawn checks the fragment (`cli::guard::unparsable_guard_arguments_allow`). The orchestrator fragment quotes its root paths, and a root that holds a quote is refused at render.
- **Record.** Every deny writes an `observations` row (`source = hook`, `event = PreToolUse:denied`, payload with the code and the classified command, never the full payload). The Health page's Safety signal counts them per role and code.

| Non-allowlisted forward | a `mutate` for spawn, land, a grant or away mode | board host allowlist; `peer serve` allowlist | refused on both hosts | `daemon::peer::spawn_not_forwardable` |
| Read-scope mutate | a `mutate` over a `read` pairing | `peer serve` scope check | `peer_refused` | `daemon::peer::read_scope_cannot_mutate` |

## 11. Unauthorized actions and detection

An unauthorized action is one of the cutover's rollback triggers (build plan, M6). The daemon checks for these at no token cost, every reconcile cycle. Each one opens a `recovery` attention item with its evidence and raises the trigger.

| Unauthorized action | Detection | Test |
|---|---|---|
| A PR of a Tiller project merged with no `approval.succeeded` for it | `pr.refresh` sees `merged` with no matching approval in `succeeded` or `executing` | `reconcile::recovery::merge_without_approval_opens_recovery` |
| A default branch moved by anything but `tiller land` | The daemon polls the remote default-branch head and compares it with the last `approval.succeeded` merge SHA or direct-push SHA | `reconcile::recovery::default_branch_move_without_land_opens_recovery` |
| An approval decided by a principal other than the owner or a grant | An `approval.decided` event whose `actor` is not `owner`, `board`, `board@<label>` whose `payload.via_peer.key_id` names an `act` key that was unrevoked when the event was written, or `daemon` with a grant id | `core::authority::decision_by_wrong_principal_raises_trigger` |
| A grant created or revoked by a principal other than the owner | The same check on `grant.created` and `grant.revoked` | `core::authority::grant_by_wrong_principal_raises_trigger` |
| A worktree with unlanded or unknown commits removed | A `worktrees` row went `gone_at` without a `run.cleaned` event | `reconcile::recovery::worktree_gone_with_active_run_opens_recovery` |
| A state row changed with no event | The property test `core::events::every_mutation_writes_its_event` in CI; at runtime, an `events` sequence gap or a `rev` that moved with no event row | `core::events::rev_change_without_event_is_reported` |

A merge by the developer's own hand on GitHub is not unauthorized: the owner can always act. Reconcile cannot tell the owner's hand merge from an agent's, so it asks the owner through the same `recovery` item (T1.2 owns the row), and the owner's answer records which it was. The config records the owner's forge login (`forge_login`, decided at CP2, C08) and the item names it when the merge was made by that login, but it still asks: workers use the same login. On a project with `merge_gate = enforced` a hand merge needs a hand edit of the ruleset first, so the case is rare there.

## 12. Testing the guards

- **Classifier tests** (CI, deterministic). Every deny and allow decision in sections 8 to 10 runs through `tiller guard pretool` with recorded hook payloads, for every role. Allow cases matter as much: a builder's `git push origin HEAD:fm/<own branch>`, `git -C <worktree> status`, quoted text that mentions `git push origin main`, and a `TaskCreate` from the orchestrator must all pass. A false block costs output (hard rule 9).
- **Fragment tests** (CI). Each role's generated fragment parses, names no unknown tool, and matches the write set and the deny list in section 8. `config_hash` changes when the fragment changes.
- **Live tests** (on demand, per host, per Claude Code version). `agents::guards::live::*` launches a real role session through the real launch form on a throwaway sandbox repo and a local bare remote, asks it to run the command, and checks a sentinel: the file was not written, the ref did not move, the PR is still open. Firstmate validated its guards the same way. They cost tokens, so they run at T4.3, at CP5, after every Claude Code upgrade, and before each host's cutover. A host where a live test fails runs that row as convention until it passes, and `host-capabilities.md` says so, except for the sandbox rows: a host whose sandbox live tests fail is not cut over (C19, section 1).
- **Land tests** use a fake forge (a trait with a recorded GitHub implementation and an in-memory one) plus a local bare repo, so head races, refused merges and unreadable results are deterministic.
