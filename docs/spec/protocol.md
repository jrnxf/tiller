## 1. Principles

1. **One writer path.** Every mutation in `state.md` section 8 is a function in `crates/core`. The CLI, the hooks, the daemon and the board API all call the same functions, so a board click and a CLI command cannot differ. The board API never writes SQL of its own.
2. **The CLI does not need the daemon.** `tiller` opens `state.db` itself (WAL, `busy_timeout` 5 s) and commits. The daemon notices new rows by polling `PRAGMA data_version` every 200 ms and pushes them over SSE. Only actions that touch the outside world on a timer or after an approval (delivery, landing, polling) need the daemon.
3. **Hooks are observations, not state** (second opinion point 11). A hook records what it saw, with `observed_at`. It never closes a card, ends a run or answers a question. Reconcile (T1.2) turns conflicting evidence into attention, never into a destructive action.
4. **Hooks fail open.** A hook that cannot write (database locked past its budget, schema mismatch, a crash) logs to `~/.tiller/log/hook.log`, exits 0 and lets the session continue. The only hooks that may change what Claude does are the PreToolUse guard (T1.4) and the Stop hook in `block-once` mode (section 2.5).
5. **AXI style.** Structured output, stable ids, documented exit codes, idempotency keys and safe retries (point 38). No command calls a model.
6. **No secrets, no account identity.** No command, response, event or log line carries an email, an account id or a token. The quota feed parses an allowlist of fields (section 8).

## 2. Ask intake

### 2.1 What is an ask

Every message the owner sends an orchestrator, and every note a script drops, is an `asks` row before the agent reads it (P27, P60). Wake-up lines (section 3) are not asks. An ask ends with exactly one disposition: `new`, `followup`, `chat` or `cancelled`. Until then it is `unresolved` and sits in the Asked column.

### 2.2 Sources

| Source | Trigger | Mutation | `asks.source` | Idempotency key |
|---|---|---|---|---|
| Owner types in an orchestrator pane | `UserPromptSubmit` hook (`tiller hook UserPromptSubmit`) | `ask.record` | `prompt` | `prompt:<claude session id>:<prompt_id>` (`prompt_id` is a common hook field [D]); when absent, `prompt:<claude session id>:<sha256 of prompt text>:<transcript byte length>` |
| Owner types in a worker pane | the same hook, in a worker session | `ask.record`, `ask.resolve followup:<run's card>` and `outbox.enqueue` (`note`) to the run's supervisor, in one transaction | `prompt` | as above |
| Hooks blocked on the host (reduced behavior) | the transcript tailer sees a user entry in an orchestrator transcript | `ask.record` | `prompt` | `transcript:<claude session id>:<entry uuid>` |
| A script or the owner from a shell | `tiller ask note <project> [--text <t> \| -]` | `ask.record` and `outbox.enqueue` (`note`) to the project's live orchestrator, in one transaction | `script` | `--key`, or a minted one (section 6.3) |
| Board ask box | `POST /api/v1/projects/{id}/asks` | `ask.record` and `outbox.enqueue` (`note`) to the project's live orchestrator, in one transaction | `board` | the send's key |
| Board "add card" | `POST /api/v1/cards` | `ask.record`, `ask.resolve new`, `card.create` and `outbox.enqueue` (`note`) in one transaction | `board` | the click's key |
| Import | `tiller import` | `import.apply` | `import` | the manifest hash |

The ask and its wake are one transaction, so a crash cannot leave a recorded ask that nobody is told about. When the project has no live orchestrator, the ask is recorded without the message, the response carries `warning: no_orchestrator`, and `session.start` enqueues one note for every unresolved ask of the project when the orchestrator starts.

On a host where hooks fire, the tailer never records asks, so one prompt cannot become two asks. Which source a host uses is the host config value `intake_source` (`hook` or `transcript`), set from the probe result (host-capabilities, "Hooks blocked by managed policy"). On a `transcript` host no hook tells the orchestrator the ask id, so the orchestrator role (T4.1) runs `tiller ask list --unresolved` at the start of each turn there.

### 2.3 What the hook tells the orchestrator

For an ask, the `UserPromptSubmit` hook returns one line of `additionalContext` [D]:

```
tiller: ask 01JC2Z8Q4M7V3R5T9W1X6Y0B2D (short X6Y0B2D) recorded. Before this turn ends run: tiller ask resolve X6Y0B2D new|followup:<card>|chat|cancelled, then send the answer with tiller reply --to X6Y0B2D. Start each line about a card with its tag, like [alpha-42].
```

It prints the full ULID once and the short form the CLI accepts (section 6.1). The orchestrator role (T4.1) carries the judgement; the hook carries only the mechanics.

### 2.4 `tiller ask resolve`

```
tiller ask resolve <ask> new --kind ship|scout|question|ops --title <t> [--priority 0-4] [--body <t> | --body-file <f> | -] [--size S|M|L] [--acceptance <t>] [--category <c>]
tiller ask resolve <ask> followup:<card>
tiller ask resolve <ask> chat
tiller ask resolve <ask> cancelled [--reason <t>]
tiller ask link <ask> new ... | followup:<card>
```

- `new` runs `ask.resolve` and `card.create` in one transaction. The response carries the card's ULID, display id and the tag to use (`[alpha-42]`).
- `chat` and `cancelled` create no card; a `--reason` goes in the `ask.resolved` event payload.
- `followup:<card>` takes a display id, a ULID or a short form. The card must be open; a follow-up on a closed card is refused with the card's outcome, and the orchestrator reopens it (`tiller card reopen`) or files a new card.
- One ask that creates or touches several cards: resolve once, then `tiller ask link` for each further card. `ask link` (`ask.link`) requires the ask to be resolved `new` or `followup` and adds an `ask_cards` row (and a card for `new`) in its own transaction.
- Retry: resolving an ask again with the same target returns the first response and writes nothing (key `ask.resolve:<ask id>`). Resolving it with a different target is refused (exit 5) with the current disposition. A resolved ask is never re-resolved; a wrong disposition is fixed by `ask link` or by editing the card.
- An ask that is never resolved stays visible in Asked with its age (point 12). Nothing resolves an ask automatically except the board's add card, which records and resolves in one transaction.

### 2.5 The Stop hook: observe mode and block-once

The Stop hook runs on every turn end in every Tiller session [D: it does not run on a user interrupt, and API errors fire `StopFailure` instead]. In an orchestrator session it also checks the intake protocol:

1. **Unresolved asks:** asks recorded for this session that are still `unresolved`.
2. **Unknown tags:** every `[<project>-<n>]` token at the start of a line in `last_assistant_message` [D] that names no card on this host. `[chat]` is always valid.

It writes one observation (`event = Stop`, `verdict = idle`) whose payload holds `unresolved_ask_ids`, `unknown_tags`, `tags` (valid card ids mentioned) and `would_block` (true when either list is non-empty). It never copies the reply into a card: the card timeline shows "mentioned in a reply at <time>" from the observation, which is enough to de-interleave without mixing discussions (point 12).

Modes, from the host config value `stop_hook_mode`:

| Mode | Behavior |
|---|---|
| `observe` (the default, and the only mode at cutover) | Record the observation. Never block. Exit 0 with no output |
| `block-once` | When `would_block` is true and the input's `stop_hook_active` is false [D], print `{"decision":"block","reason":"<one line naming each unresolved ask and unknown tag>"}`. When `stop_hook_active` is true, never block, so one turn is blocked at most once. Workers are never blocked by this check |
| `off` | Record only the turn end, no intake check |

**The switching rule.** Observe mode measures what blocking would have done. A `would_block` stop is a *false block* when, within 2 minutes and without another owner prompt, the same session resolves every listed ask and every unknown tag turns out to be a card created in that window. `tiller intake stats` reports the stop count, the would-block count and the false-block rate over a window. The owner may switch to `block-once` only when the last 7 days hold at least 200 orchestrator stops and the false-block rate is under 2% (numbers accepted at CP2, C14). The switch is a config change the owner makes (`tiller config set stop_hook_mode block-once`), never automatic, and it is recorded as an event (`config.changed`). `config set` refuses the switch to `block-once` (exit 5, with the current stats) while the rule is not met. Switching back to `observe` is always allowed.

**The owner guard.** In an orchestrator session the Stop hook also asks whether the last message solicits a reply from the owner. If it does and the session opened no attention item since the turn began (its last prompt or wake-up line), the hook blocks the stop once with `{"decision":"block","reason":...}`. The reason tells the orchestrator to open an item with `tiller attention open <card> --kind decision ...`, or, if it was not asking the owner, to end the turn again. When `stop_hook_active` is true the hook never blocks, so one turn is blocked at most once, and an intake block (above) comes first. Workers are never checked, and `stop_hook_mode = off` turns the guard off with the rest. The Stop observation's payload gains `asks_owner` and `opened_attention`. It never holds the message text.

**The reply guard.** Under the owner guard, and on the same terms (an orchestrator session, `owner_guard.enabled`, `stop_hook_active` false, never a worker), the hook also blocks a stop once when the turn resolved an ask and sent no reply: an ask this session resolved since the turn began, with any disposition but `cancelled`, that no `tiller reply` answers. The reason names each such ask and the command, `tiller reply --to <ask> --text "..."`, then says to end the turn again. An intake block or an owner-guard block comes first, so one turn is still blocked at most once. The Stop observation's payload gains `unreplied_ask_ids`, on every orchestrator stop the guard checks. The guard reads only ids: the reply's words are stored by the orchestrator's own `tiller reply`, never by a hook.

The check is a keyword rule over the message (code blocks, URLs and markup removed first). When the rule says no and a decision key is set, `owner_guard.decider_key` or the `PERPLEXITY_API_KEY` environment variable, a decision model gets a second look: the hook sends one POST to `https://api.perplexity.ai/v1/decisions` (model `pplx-decider-flash-v1.2`, question "does the message solicit a current response or decision from the human owner?") with a 2 s timeout. A probability at or above `owner_guard.threshold` (default 0.3) counts as yes. An error, a timeout, a bad answer or no key keeps the rule's answer.

**Privacy.** With no key, nothing leaves the host. When the owner sets a key, the orchestrator's last message of each turn whose rule answer was no is sent to Perplexity. The key is never logged or printed: `tiller config get` and the `config.changed` event show `<set>`, and the Stop observation never holds the message.

| Host config value | Default | Meaning |
|---|---|---|
| `owner_guard.enabled` | `true` | `false` turns the owner guard off |
| `owner_guard.decider_key` | none | The decision model's API key. Without it the guard is rule-only |
| `owner_guard.threshold` | `0.3` | A probability at or above this counts as yes (0 to 1) |
| `owner_guard.endpoint` | the URL above | Another decision endpoint, https only (plain http only for loopback) |

The turn-end guard Firstmate keeps (P26, never go idle with work in flight) is not a block here: the daemon delivers pending outbox messages to an idle orchestrator (section 3), which wakes it.

## 3. Wake-up lines and the inbox

### 3.1 Format

The outbox (`state.md`, Outbox) stores every message first. The pane only ever receives one wake-up line, typed by the daemon through the terminal holder [H] and followed by Enter:

```
tiller inbox <ULID>[ # <kind>[ <display id>]]
```

for example `tiller inbox 01JC2ZB6N0E2K4M6P8R0S2T4V6 # steer alpha-42`. The comment is for the person watching the pane; it carries no data. The grammar, as a regex on the whole submitted prompt with surrounding whitespace trimmed:

```
^tiller inbox [0-9A-HJKMNP-TV-Z]{26}( # (wake|steer|answer|note)( [a-z][a-z0-9]*(-[a-z][a-z0-9]*)*-[0-9]+)?)?$
```

The project part of the display id is also 2 to 32 characters (`state.md` section 2).

### 3.2 How hooks recognize it

The `UserPromptSubmit` hook matches the prompt against the grammar before anything else:

- **A match is never an ask.** The hook looks up the outbox row. If the row's `target_session_id` is this session, it runs `outbox.ack` (actor `hook`) and returns the message body, plus the body of every other `pending` or `delivered` message for the same session (each acked in the same transaction, oldest first), as `additionalContext`. The agent reads its messages without a tool call.
- **A match for another session** (a stale pane, a retargeted message): the hook does not ack. It records an observation `wake_mismatch` and returns one context line telling the agent to ignore the line. Reconcile retargets the message (`state.md`, Outbox rules).
- **Edge cases.** An id with no outbox row, or a session the hook cannot map, is treated as a mismatch: no ack, one context line. A row already `acked` returns its body again and writes nothing. A row in `failed` returns its body with a note that it was given up on, and writes nothing; reconcile owns it.
- **No hooks on the host:** the agent runs the typed line as a command. `tiller inbox <id>` performs the same ack and prints the same bodies. The role files tell every agent to run a line of that shape when it sees one.
- The transcript tailer treats a matching user entry the same way it treats a hook match: it records the wake, it never records an ask.

Because the line is recognized, a board-created card (already recorded and resolved) is never created a second time by the orchestrator reading its wake-up line (point 13; T4.4 acceptance).

### 3.3 Delivery rules

T2.5 implements these; they are listed here because they are part of the contract a session sees.

- **Store, then type.** `outbox.enqueue` commits before any keystroke. A crash between store and send leaves a `pending` row that the next delivery pass sends.
- **One line per batch.** When several messages are pending for one session, the daemon types one line naming the oldest; the ack returns them all. A worker's done, blocked or decision therefore reaches the orchestrator once, without flooding the dialog (P20).
- **Target check.** [H] Before typing, the daemon reads the pane from the holder (`get`) and checks that its `key` is the target session. The holder never reuses a pane id, so a mismatch is a bug and is logged as one (`terminal-holder.md` 4.4). A mismatch retargets or fails the message; it never types into the wrong session.
- **Empty composer.** It also reads the pane's composer (the holder's `screen` read of the visible screen, `format: ansi` [H]) and types only on a positive `empty` verdict, as Firstmate's herdr backend does. A composer holding text (the owner's half-typed draft) or one that cannot be read defers delivery (`next_attempt_at`, 30 s); the daemon never clears it, since the text may be the owner's. A composer holding exactly the wake-up line for one of the session's unacked messages (however its rows wrapped) is that line typed but not submitted, and is finished with Enter; a draft that merely starts with one is the owner's. A bare shell prompt is never an empty composer: it means the agent is gone, and the message waits for a successor (recovery.md, R09). The line is typed once; only Enter is retried.
- **Verified submit.** Claude Code can read an Enter that arrives right after typed text as part of it, adding a newline instead of submitting; a Claude just relaunched in the same pane does this every time. So the daemon waits half a second between the line and Enter, then reads the composer back and presses Enter again while the line is still there, up to four presses a pass. One pass types every session's line first, pauses once for all of them and records each session as soon as its own line is shown to have left, so a pane that is slow to take its line never delays the others. A message is `delivered` only on evidence the line left: the composer reads empty, busy or behind a dialog, or the hook acked the batch. Other text or an unreadable screen is read again, never pressed. A line not shown to have left stays `pending`, deferred 30 s, and the next pass finishes it with Enter. After three such passes the line is left like the owner's text and reported after 10 minutes.
- **Busy panes wait.** A session whose effective activity is `working` or `waiting_permission`, or whose pane shows a dialog, defers delivery (`next_attempt_at`).
- **Re-ring.** A `delivered` message not acked after the idle threshold, with the session observed `idle`, is typed again (P23). The threshold is T1.2's.
- **Polling pickup.** `tiller inbox` with no id lists and acks every pending or delivered message for the calling session. It is how a session drains its inbox when it suspects a missed doorbell.

### 3.4 Notifications (P36)

The daemon sends the owner a desktop notification [H] by running the command in `[notify] command` of `~/.tiller/config.toml` (`terminal-holder.md` section 7) only when something new needs them, once per cause, never for a routine turn. Each host runs its own command for its own agents. The command gets one JSON object on stdin, in the shape of a Claude Code `Notification` hook event (`hook_event_name`, `notification_type: "tiller"`, `title`, `message`, `session_id`, `cwd`), and the env `TILLER_SESSION_ID`, `TILLER_PANE` and `TILLER_HOST`. With no command set, the daemon sends nothing and `tiller doctor` warns that owner notifications are off:

| Cause | Once per |
|---|---|
| An attention item opens (`attention.opened`), including a `merge` item for a PR ready for the owner's word | item |
| A session has been in `waiting_permission` or `waiting_input` for 30 minutes (recovery.md, thresholds) | session, per prompt |
| A reboot restore finished (recovery.md, R04) | boot |
| A lost holder's restore finished [H] (recovery.md, R21) | holder instance |
| The daemon entered read-only mode (recovery.md, R10, R11) | episode |

The notification names the project and the card, and opening it attaches to the project's orchestrator [H]: the owner's notification app runs `tiller attach "$TILLER_SESSION_ID"` in the terminal app, or `ssh -t <host> tiller attach ...` for a card from another host (`terminal-holder.md` section 7). A re-ring, a worker's status line, a PR event or a card moving between columns never notifies. Each notification is recorded in the event that caused it (`notified_at` in the payload), so a daemon restart cannot send it twice. Test: `delivery::notify::new_attention_item_notifies_once`. T2.5's notifier (`delivery::notify`) covers the first row: it records `attention.notified` (`state.md`, `notification.record`) before it sends, so it never sends twice. The record only says the daemon tried, so the send then writes one outcome and never retries: `attention.notify_sent` (`notification.sent`) when the command took it (exit 0 within 10 s [H]), `attention.notify_failed` (`notification.fail`) when it refused it (any other result, with its stderr in the message [H]). A crash between the record and the outcome leaves the record alone. The card timeline shows one line per notification: "notified you about an item" after a sent outcome, "could not notify you about an item" after a refused one, and "tried to notify you about an item" for a record with no outcome. The recap lists none of the three kinds: the item's own `attention.opened` line is the news, and a failed ping shows on the card timeline and in the daemon log. Only items opened in the last hour count as new. Tests: `daemon::notify_timeline::a_notification_herdr_took_reads_as_sent`, `daemon::notify_timeline::a_notification_herdr_refused_does_not_read_as_sent` (H13 renames both for the notify command), `daemon::notify_timeline::a_record_with_no_outcome_reads_as_tried`. The reboot row is recovery's (`reconcile::recovery::reboot_resumes_workers_in_own_worktrees`).

### 3.5 Review-page answers (P47)

Decided at CP2 (C05): in v1. A worker that publishes a live review page records it with `artifact.add` (`state.md`, Artifact), and the owner's annotations on that page reach the worker through the outbox, not through the worker polling the page.

- **Source.** A T2.5 poller reads the review page tool's feedback queue for every `page` artifact that is not retired and has a path and a run. It runs on the daemon's schedule (every 30 s) and records its last success in `/health` like every poller. A page's artifact record gives both its `--url` and its `--path`: the URL is what the owner opens, the path is what the poller reads.
- **Reading.** The reader runs `lavish-axi poll <page> --owner tiller --timeout-ms 1500` for each live `page` artifact that has a `path` and a run, never with `--takeover`: a page whose listener belongs to someone else reads as quiet, and a page the owner ended is left alone for ten minutes, then asked again, since the owner can reopen it for another round. Every call to the tool, polls and `end` alike, carries `LAVISH_AXI_ALLOWED_HOSTS` from `[spawn] review_allowed_hosts`, because a call can be the one that starts the server and the server reads it once. The reader understands the table form of the `prompts` array and the list form `lavish-axi` prints when a prompt carries an attachment; a `prompts` array it cannot read is an error in `/health`, never a quiet page. A read consumes the queue, so the entries are stored in the pass that reads them; a crash between the read and the store loses that batch and the owner annotates again. The tool is the `[spawn] lavish` command (`TILLER_LAVISH_AXI` replaces it).
- **Delivery.** Each new feedback entry becomes one `outbox.enqueue` of kind `steer` to the live session of the run that published the artifact (`artifacts.run_id`), with actor `daemon` (the role matrix in `authority.md` gives the daemon the steer right and gives scripts none). The message body is the entry's text and the element it annotates, never the page itself. The ordinary delivery rules apply (3.3): store, then type; one line per batch; busy panes wait.
- **Idempotency.** The key is `page:<artifact id>:<feedback entry id>`, so a re-poll, a daemon restart or a second poller pass never delivers an entry twice.
- **No owning session.** When the publishing run has ended, the entry goes as a `note` to the project's live orchestrator instead, which decides whether to start a run for it. An entry for an artifact whose card is closed is recorded as an event on the card and wakes nobody.
- Test: `delivery::sources::page_answer_reaches_owning_worker`, plus `delivery::sources::page_answer_replay_is_not_delivered_twice`.

## 4. Hook events

### 4.1 One entry point

Every hook Tiller installs runs `tiller hook <event>`, with the hook input JSON on stdin, except `PreToolUse`, which runs `tiller guard pretool --role <role>`, the one decision owner `authority.md` names; it records the same coalesced observation as the other tool events. Tiller registers hooks in project or local scope, never user scope (host-capabilities), and only for events whose handler below is not `ignore`. The input struct keeps unknown fields (`#[serde(flatten)] extra`), so a new Claude Code field never breaks a hook. The observation payload is a per-event allowlist of fields, not the raw input: `prompt`, `last_assistant_message`, `tool_input`, `tool_response` and `error_details` are never stored, because they can hold whole replies, file contents or secrets. An ask's text lives only in `asks.text`, and the Stop hook stores only the tags it extracted. T2.6 snapshots each event's allowlist.

Observations are append-only. A hook delivered twice with identical input is written once: the handler keys it `hook:<claude session id>:<event>:<sha256 of the input>` in `idempotency_keys`.

The handler resolves the Tiller session in this order: the `TILLER_SESSION_ID` environment variable set at launch, then `sessions.claude_session_id = session_id`, then none. An unmapped event is still recorded (`observations.session_id` null) so reconcile can bind it later.

Budget: p95 under 10 ms with the daemon down (T2.6 acceptance). A handler that needs more (none in this table) must move the work to the daemon.

Hook files stay bounded. A write that finds `~/.tiller/log/hook.log` at 1 MiB or more first renames it to `hook.log.1`, replacing the one before, so the two hold about 2 MiB at most. The size check is one `fstat` on the file the hook already opened, and only a hook that logs pays it. A spool file the daemon cannot import is renamed `<ulid>.json.bad` in `~/.tiller/hook-spool/`, and each daemon pass that gets through the spool keeps only the newest 100 of them, deleting the rest and logging how many went. The hook itself never prunes.

### 4.2 Event to handler

Claude Code documents 33 hook events [D]. Each maps to exactly one handler. `event` is the value written to `observations.event`; `verdict` is the activity it implies, or null when it implies none (`state.md`, Observation).

| Hook event | Handler | `observations.event` | Verdict | Also |
|---|---|---|---|---|
| `SessionStart` | `session_bind` | `SessionStart:<source>` (`startup`, `resume`, `clear`, `compact`, `fork`) | null | `run.bind_session`: binds `claude_session_id` and the pane; the model goes in the payload. On `clear` or `fork` the Tiller session row is rebound to the new Claude id and the old id goes in the payload. It fires before the login is checked [T], so it never proves the session works. On `resume`, `clear` or `compact` the daemon runs `mem.load` (`memory.md`, section 7) on this observation, copying the session's newest load set under the new trigger; the launch wrote the `startup` rows. The hook itself hashes nothing, so it stays inside the 10 ms budget |
| `Setup` | `ignore` | - | - | Tiller never launches with `--init` or `--maintenance` |
| `UserPromptSubmit` | `intake` | `UserPromptSubmit`; `wake` for a wake-up line for this session; `wake_mismatch` for any other wake-up line | `working` | section 2 for asks, section 3.2 for wake-up lines |
| `UserPromptExpansion` | `ignore` | - | - | `UserPromptSubmit` records the prompt the owner typed |
| `PreToolUse` | `guard` (`tiller guard pretool --role <role>`) | `PreToolUse` (coalesced, 4.3) | `working` | the allow or deny decision is `authority.md`'s (P58, P59) |

### 4.3 Coalescing

`PreToolUse`, `PostToolUse` and `PostToolUseFailure` fire on every tool call. Their handlers write an observation only when the session's `activity` is not already `working` or its `activity_observed_at` is older than 60 s. The verdict stays fresh for staleness without a row per tool call.

|---|---|---|---|

The deploy watch (decided at CP2, C02 amended by S07). A run counts for the watch only when it matches both the commit and the environment:

- **Commit.** Its `head_sha` equals the pushed SHA, or descends from it on the default branch (the superseded case). A run for an older commit never counts, however recent it is.
- **Environment.** When `projects.deploy_environment` is set, the run must have a job that deployed to that environment (`gh-axi` reads the run's deployments). A run of the same workflow that skipped the environment, or deployed only to another one, does not count. When it is null, the workflow run's own conclusion is the result.
- **Results.** `success`, `failed`, `cancelled`, `superseded`, `missing` (no matching run 10 minutes after the push) and `timed_out` (a matching run not concluded by `deploy_timeout_minutes` after the push). `state.md` section 7 says what each one records; only `success` and `superseded` close the card.
- **Idempotency.** `deploy.record` is keyed by the obligation id, the run id and the result, so a re-poll writes nothing new. `missing` and `timed_out` are written once per watch; a later matching conclusion still resolves the watch.
- Tests: `daemon::forge::deploy_success_must_match_sha_and_environment`, `daemon::forge::deploy_for_older_commit_does_not_count`, `daemon::forge::superseded_deploy_closes_landed`, `daemon::forge::missing_and_timed_out_deploys_open_recovery`.

## 5. Transcript tailing

- **Path.** `<config dir>/projects/<slug>/<claude session id>.jsonl`, where the slug is the physical working directory with every character that is not a letter or digit turned into `-` (host-capabilities [T]). The tailer derives it from the session's cwd and Claude id and stores it in `sessions.transcript_path`. Subagent transcripts under `<slug>/<session id>/subagents/` are not tailed.
- **Mechanism.** The daemon watches each session's transcript, while the session is live and for the retention window below, with `notify` and reads appended lines only. It keeps the byte offset in memory and writes it, with the file it was read from, into each observation's payload (`transcript_offset`, `transcript_path`), so a restarted tailer resumes from the newest offset recorded for that session and that file, and never records an entry twice. A tailer belongs to one session and one file: when `/clear` or a forked resume binds the session to a new transcript, the old file is read once more to its end and let go, and the new file is read from its head. A file with no offset of its own while the session has other transcript rows (another file's, or rows from before the path was stored) is read from 0 and deduped by entry uuid. A truncated or replaced file (offset past the end) also restarts from 0 and dedupes by entry uuid. Either dedupe reads the uuids of the session's transcript rows once and checks every later entry against them, wherever the repeats sit in the file. Tests: `observe::tailer::resume_takes_the_offset_of_its_own_path_only`, `observe::tailer::rows_without_a_path_are_read_again_and_deduped_by_uuid`, `observe::tailer::a_file_copied_after_resume_is_still_deduped`, `observe::tailer::truncated_transcript_restarts_and_dedupes_by_uuid`, `daemon::workers::transcript_tailer_follows_a_cleared_session_to_its_new_file`, `daemon::workers::transcript_tailer_after_a_restart_reads_a_new_file_from_its_head`.
- **Lag.** Claude Code writes the transcript asynchronously [D]. Transcript observations use the entry's own timestamp as `observed_at`, so a late read never moves the projection backwards (`state.md`, out-of-order rule).
- **What it records.** Interrupts on every host (Stop does not fire on them [D]). On hosts with `intake_source = transcript`, also the rows in 4.5 that hooks would have given. It never records tool calls one by one; it coalesces like 4.3.
- **Privacy.** Transcript text is never copied into an observation payload except an ask's text into `asks.text` on reduced hosts. Raw transcripts are read only and never committed (`state.md`, section 9).
- **Retention.** The tailer stops watching a session 10 minutes after it ends. In that window it reads the file the session was bound to when it ended, where Claude Code writes its last lines. A file the session left earlier is still read once more and let go at once, as above. When the window closes the file is let go without a read, so a line appended after it is never recorded. A daemon started inside the window resumes the file like any other. A line read in the window is recorded as a row, but an ended session never looks live again: a session ended with no `ended` verdict (a relaunch, a failed spawn) may still settle, but only forward, from a live state to `idle`, `errored`, then `ended`. An entry stamped after the end opens no ask. Tests: `daemon::workers::transcript_tailer_reads_an_ended_session_for_ten_minutes_then_stops`, `daemon::workers::transcript_lines_after_the_end_leave_an_ended_session_ended`, `daemon::workers::an_ended_session_settles_only_forward`, `daemon::workers::transcript_tailer_keeps_only_an_ended_session_s_last_file`.

## 6. The `tiller` command surface

### 6.1 Conventions

- **Ids.** Every response names entities by ULID (`id`) and, for cards, `display_id`. Inputs accept a ULID, a short form (its last 7 characters, from the random part; a prefix would be shared by every id minted in the same minutes), or a display id where the entity has one. Responses print the short form beside each ULID. A run is addressed as `<display id> <role>` (`alpha-42 build`) or its name (`alpha-42-build`, `alpha-42-build-2`; called the herdr name before the cutover [H]); the short role names are `scout`, `build`, `review` and `verify` for the roles `scout`, `builder`, `reviewer` and `verifier`. An ambiguous short form fails with exit 3 and lists the candidates.
- **Output.** The default is TOON, the compact form the axi tools print, for agents. `--json` prints the stable JSON contract, which insta snapshots (T2.2). Both come from one serde struct. Every response has `ok`, `data`, and, for a mutation, `events` (the `seq` values written) and `replayed` (true when an idempotency key matched). A response may end with `help` lines naming the next useful command, as gh-axi does. Diagnostics go to stderr; stdout is only the response.
- **Errors.** `{"ok":false,"error":{"code":"<code>","message":"<readable>","entity":"<entity>","id":"<id>","current":{...},"hint":"<next command>"}}`. The `conflict` message follows `state.md`: `conflict: card 01J... is at rev 7, you sent 5; title is now "<value>"`. A project conflict adds `; it changed <Lisbon weekday and time>` and carries `edited_at` in `current`.
- **Times.** JSON carries RFC 3339 UTC. TOON shows Europe/Lisbon with the weekday (`Tue 2026-11-03 14:00`). A date input without a time (`--until 2026-11-07`) means 09:00 Lisbon that day; an input with an offset is taken as given.
- **Actor.** Inside a session Tiller launched, `TILLER_SESSION_ID` (and for workers `TILLER_RUN_ID`) are set at launch, and the actor is `session:<id>`. The daemon is `daemon`, a hook is `hook`, and anything else on the owner's shell is `owner`. T1.4 decides which actor may run which command; a refusal is exit 6.
- **Owner marker.** Every mutation refuses with exit 6 (`owner_marker`) while `~/.tiller/owner` names another system. Reads always work.

### 6.2 Exit codes

| Code | Name | Meaning | Safe to retry |
|---|---|---|---|
| 0 | `ok` | done, or replayed from an idempotency key, or already in the requested state | - |
| 1 | `internal` | a bug or an unreadable database | after a fix |
| 2 | `usage` | bad arguments | no, fix them |
| 3 | `not_found` | no such entity, or an ambiguous prefix (candidates listed) | no |
| 4 | `conflict` | `expected_rev` is stale; the current value is in `current` | after re-reading |
| 5 | `refused` | a precondition failed (`state.md`, section 8); the failed fact is named | after the fact changes |
| 6 | `forbidden` | the actor may not do this (T1.4), or the owner marker names another system | no |
| 7 | `unavailable` | database busy past `busy_timeout`, the daemon is needed and down, or the terminal holder [H] or the forge is unreachable; nothing was written | yes, same key |
| 8 | `uncertain` | an outside action was sent and its result could not be read: `tiller land` (the approval is `uncertain`), or a mutation forwarded to a peer (10.3, 504 `forward_uncertain`) | `land`: no; reconcile resolves it from the forge. A forwarded mutation: yes, same key, since the peer applies a key once |

Hooks always exit 0, except what the PreToolUse guard (T1.4) and the Stop hook in `block-once` mode print as their decision.

### 6.3 Idempotency

Every command is in one of three classes, named in the tables below:

- **natural:** a transition guarded by its preconditions. The command first checks whether the entity is already in the target state with the same arguments; if so it returns the current state with exit 0 and `replayed: true` and writes nothing, before any precondition runs. Otherwise the preconditions apply, and a different target is refused (exit 5). An edit whose fields all equal the current values is a no-op the same way only at the current `rev`; a stale `rev` is always a conflict (exit 4), even when the values already match, because two writers that compute the same value from one stale read must not both succeed. Only a keyed edit replays at a stale `rev`: a known key returns the stored response.
- **keyed:** a create or an append. It carries an idempotency key; a known key returns the stored response from `idempotency_keys` and writes nothing (`state.md`, invariant 10). A key replays only for the command, the actor and the arguments it was first used with. The same key from another actor is refused (exit 5) and returns nothing of the first request. So is the same key with other arguments, when both requests recorded the SHA-256 of their normalized arguments (`state.md`, Bookkeeping); a retry must resend the same arguments, and new arguments need a new key. The CLI sends the arguments with every key it resolves: a `--key`, a derived key or a minted one, and the `--key` of `card edit` too. `tiller card create alpha ... --key k` and then `tiller card create beta ... --key k` is refused (exit 5) and writes nothing. A key stored before schema 15 records no actor or arguments and replays on the command alone. Keys come from `--key <k>`, or, when the caller is a Tiller session and gives none, the CLI derives `auto:<session id>:<command>:<sha256 of the normalized arguments>:<turn anchor>`. The turn anchor is the id of the session's newest turn-boundary observation (`UserPromptSubmit`, `wake`, `Stop`, `StopFailure`, `interrupt`, or `transcript:turn_end` on a hook-less host), so a retry inside one turn replays and the same command after the next turn boundary is new. Hooks and the board always send a key. The daemon binds a board key to its request: it records the SHA-256 of the method, path, query and JSON body (object keys sorted, so field order and spacing do not matter). The body's top-level `rev` is left out, since it is a precondition and not an argument: a retry that read the newer `rev` its own write made still replays. A shell caller (the owner, a script) that gives no key gets a fresh key minted and printed in the response; repeating the command with `--key <printed key>` replays, and repeating it without one creates again. So without `--key` each owner run is a new request, and the CLI never derives an owner key from the arguments, because the same text sent twice can be on purpose. Pass `--key` to make a retry safe. A natural command (`hold`, `unhold`, `close`, `complete`, `cancel`, `reopen`, `dep add`, `dep rm`, `withdraw`, the admin commands) needs none: a second run replays or is refused, and writes nothing more.
- **not idempotent:** named, with the reason: a keyed command run from a shell without `--key` (by design: a weekly script may send the same note twice on purpose, and the minted key makes the retry path explicit), `tiller agent interrupt` (`POST /api/v1/agents/{session}/interrupt` carries a key, and a retry of that key sends no second Escape), `tiller land` once its merge call is sent, and `tiller board` (each call mints a new one-time login link and code). Each says so in its help.

Keys expire after 30 days (`state.md`, Bookkeeping).

**Dispatch rules (P02; decided at CP2, C04).** The model and effort of every run come from a `[dispatch]` table in `~/.tiller/config.toml`, which fleet roles cannot read or write (`authority.md`, section 8). It holds an ordered model list (cheapest first), the effort order `low` < `medium` < `high` < `xhigh` < `max`, and rules keyed by card kind and size, each naming a model and an effort, with a default rule for anything unmatched. `run.start` resolves the rule inside its transaction and writes the resolved model, effort and the rule that matched into the `run.started` payload. `tiller spawn --model M --effort E` from the orchestrator may raise either value above the rule and is refused (exit 6, naming the rule) below it, since a downgrade needs the owner. The owner lowers or raises it for one card with `tiller card edit <card> --dispatch <model>:<effort>`, which sets `cards.dispatch_override` (owner only; `state.md`, Card); an override wins over the rule and is quoted in the payload. T4.2 enters the shipped defaults: small on haiku low, medium on sonnet medium, large on opus medium, anything else sonnet medium. A `PostModelSwitch` that leaves the resolved model is recorded as drift (4.2). Test: `agents::spawn::dispatch_resolves_model_effort_from_rules`, plus `agents::spawn::orchestrator_downgrade_refused`.

## 7. Board API

### 7.1 Transport and safety

- The daemon serves `http://127.0.0.1:7421` only, never another interface (AGENTS.md).
- **Host check.** Every request must carry `Host: 127.0.0.1:7421` or `localhost:7421`; any other value gets 421. This stops DNS rebinding. The owner can name extra hosts with `tiller daemon --allow-host <host>` (repeatable, exact match, no wildcards; home-manager's `programs.tiller.daemon.allowHosts`): the name of a reverse proxy that terminates TLS and forwards to the daemon with the browser's `Host`. Such a name gets the whole board, but only to a browser signed in with the owner cookie (Credential, below), and its mutations pass the same checks as loopback's with one difference: their `Origin` must be `https://<that host>`, never `http://`. The daemon itself still speaks plain http on 127.0.0.1 only; it trusts no forwarded header for access, and an allowed host's `https://` origin is the browser's own word that the page came over TLS. The one forwarded header it reads is `X-Forwarded-For`, and only to count sign-in code tries per client (Credential, below), so the proxy should set it, as common reverse proxies do.
- **Credential.** `authority.md` (Board API credential) owns the requirement; this is the mechanism. On loopback, reads (`GET`, including the SSE stream) are served to any request that passes the Host check, so the CLI and a local board need no cookie to read. At an `--allow-host` name every read needs the owner cookie as well: without it the daemon serves only the signed-out screen (the app shell, with no boot snapshot inlined, and its static assets), the login link and `POST /api/v1/login`; every other request there, `GET /api/v1/session` included, gets 403 `signed_out`. The terminal mirror is the one exception on loopback: watching an agent's pane writes nothing, but it shows whatever the pane shows, so it is a `POST` with every mutation check below (7.4, Terminal mirror). Mutations need the owner cookie, `tiller_owner`, `HttpOnly; SameSite=Strict; Path=/`, which the browser sends with `fetch` and `EventSource` alike. It is minted only through the one-time login link `tiller board --login` prints (`GET /login/<one-time token>` sets it and redirects to `/`); `GET /` never sets it. The link names `http://127.0.0.1:<port>`, and with allowed hosts also `https://<host>` for each (a host is an exact name or address with an optional port, never a pattern; `:443` is dropped, since a browser leaves it out of `Host` and `Origin`), plus a QR code of that link on stderr when stderr is a terminal, so a phone can scan it; the hosts come from `daemon.json`, where the running daemon records them. Next to the link it prints an 8-digit code, which the board's signed-out screen asks for in its one field: `POST /api/v1/login` with `{"code": "<8 digits>"}` sets the same cookie and answers `{"owner": true}`. The link and the code are one login: either works once, at any of those hosts, and only for one minute, and using one spends the other. The board may be public, so anyone can type codes; the limits on them count per client, so a stranger's wrong codes spend only the stranger's own tries. A client is the browser's address: the last `X-Forwarded-For` entry, which the proxy appends (entries before it are the browser's own word and are ignored), an IPv6 address cut to its /64, and loopback when the header is absent; all tries whose last entry is no address share one client of their own. An IPv6 client also counts against its network, the /48 around it, since one subscriber can hold a whole /48 for free. A wrong code is 403 `wrong_code` and counts against every pending code that client may still use; on that client's third wrong code, or its network's tenth, a pending code burns for that client or network (403 `code_burned`): it refuses that code from there, even the right one, while the code works for every other client and its link works for everyone. A code minted later starts afresh, so `tiller board --login` always gives a code the owner can use. Each client may try at most 10 codes a minute, and each IPv6 network 30 (429 `too_many_tries`, nothing checked). One limit is shared: a pending code burns for everyone, its link aside, on the 1000th wrong code from all clients together. Why: a code is one of 10^8 and lives one minute, so 1000 wrong codes cap the chance that guessing finds it at 1 in 100,000, however many addresses the guesser holds, and since each client has only three and each network ten, denying the owner the code takes 334 IPv4 addresses or 100 IPv6 networks guessing within that minute; the link and QR code still work then. The network count has one cost: an owner on IPv6 who shares a /48 with a guesser (some mobile carriers pool many subscribers in one) loses that code to the guesser's ten wrong codes, though not the link, and a fresh code starts afresh. The per-client counts live in the daemon's memory, so a restart forgets them (a guesser gains three more tries a code from each client, ten from each network), while the shared count is stored with the pending login. The counts are only as good as the proxy's last entry. A proxy that does not set `X-Forwarded-For` lets a guesser name any address: that buys it more tries, never past the shared 1000, and lets it spend the tries of an address it names; a proxy that passes on no header at all puts every browser in loopback's one client. Behind a chain of proxies (a CDN in front of the one that forwards to the daemon), the last entry is the previous hop, so every browser that came through one hop shares its count; the board then needs the forwarding proxy to rewrite the header from the real client address (for nginx, `real_ip_header` with `set_real_ip_from` for the CDN). Only the code's hash is stored, and the daemon never logs it. At an allowed host the cookie is also `Secure`, since that host is reached over https; a proxy serving it over plain http therefore cannot sign a browser in. It survives daemon restarts, so open tabs keep working, and expires 30 days after it was minted (`Max-Age=2592000`, and the stored hash carries the same expiry, so a copied cookie stops working too); after that, `tiller board --login` must be run again (decided at CP2, C15). Its hash is stored under `~/.tiller`, which every fleet role is denied. A mutation also needs `Content-Type: application/json`, `Sec-Fetch-Site: same-origin` and the board's own `Origin`: `http://<Host>` on loopback, `https://<Host>` at an allowed host; so does `POST /api/v1/login`. No CORS headers are sent, so another site's page can neither read nor write.
- **Sign out.** Settings' Sign out sends `POST /api/v1/logout`, which passes the same checks as a mutation, owner cookie included. It deletes that cookie's stored hash, so the cookie stops working everywhere, ends the event streams and terminal mirrors opened with it at an allowed host, and clears it from the browser (`Max-Age=0`). Such a stream also re-checks its cookie every minute, so one that expires ends without a sign-out. At an allowed host the board then shows the signed-out screen; on loopback, where reads need no cookie, it stays, read-only, and Settings shows this browser as not signed in. A sign-out refused as `signed_out` means the cookie was already gone, and the board shows the signed-out screen too. Other browsers' cookies stay. `GET /api/v1/session` answers `{"owner": true}` when the request carries a live owner cookie, else `false`; at an allowed host, without one, it is 403 `signed_out` like every other read.
- **Peer forwarding.** A mutation aimed at a paired peer's record (7.4, `host`) passes every check above on this host first, then travels to the peer over the peer link (section 10.3) and is authorized again there. The owner cookie never leaves this host, and the peer never accepts a cookie from elsewhere. A mutation through an `--allow-host` name is forwarded on the same terms once it has passed this host's checks.
- **Same-user processes.** A process running as the owner's OS user that can read `~/.tiller` could still act as the owner. `authority.md` closes this for fleet roles (no access to `~/.tiller`, no localhost from the sandbox) and lists it as an alternate path with tests.
- **Versioning.** Every path is under `/api/v1`. The OpenAPI document (`contract/openapi.json`, utoipa, T2.8) is the board's only source of types, including the SSE event schemas.

### 7.2 Responses

Mutations return the CLI's response shape (6.1) plus a receipt:

```json
{"ok": true, "replayed": false, "events": [4182, 4183],
 "receipt": {"recorded_at": "2026-11-02T14:05:09.123Z", "outbox_id": "01JC...", "approval_id": null},
 "data": { "...": "the changed entity" }}
```

The receipt's three stages (point 36) come from records, not from the response: **recorded** is the commit (this response), **delivered** is `outbox.state = delivered` or `approval.state = executing`, **done** is `acked` or `succeeded`. The board follows the later stages over SSE.

| HTTP | CLI exit | When |
|---|---|---|
| 200 | 0 | done or replayed |
| 400 | 2 | bad body |
| 403 | 6 | forbidden, owner marker, missing or bad owner cookie; `signed_out`: a request at an `--allow-host` name without it; `wrong_code` and `code_burned`: a sign-in code refused (7.1) |
| 404 | 3 | not found |
| 409 | 4 | stale `rev`; body has `current` |
| 421 | - | wrong `Host` |
| 429 | - | `too_many_tries`: more sign-in codes this minute from one client, or one IPv6 network, than the daemon takes (7.1); `too_many_streams`: a session that already holds 64 open SSE streams (7.5) |
| 422 | 5 | precondition refused; `label_taken`: Add a host's label is this host's or already paired; `already_paired`: Add a host's alias, or the host it reaches, is paired under another label |
| 502 | 6 | `peer_refused`: the owning peer refused a forwarded mutation's credential (revoked key, read scope, op not allowlisted, owner marker there); nothing written there. Also a new host that refused Add a host's pairing (10.1); nothing written here |
| 503 | 7 | unavailable; nothing written. Before `tiller init` every read and write answers 503 with a two-line `hint`, one command per line in the order to run them: `tiller owner set tiller` (init refuses while the owner marker names another system; the command is a no-op when it already says tiller), then `tiller init --host-label <label> --lane-capacity <n>`. The board setup screen shows each line as its own numbered command, with what it does. Also `peer_unreachable`: the owning peer's link is not `live`, so nothing was sent, or ssh did not reach the new host for Add a host (10.1) |
| 504 | 8 | `forward_uncertain`: the frame was sent and no result came within 10 s; nothing is held for a retry. The owner may retry from the control, which reuses the same `idempotency_key`, so the peer answers from its stored response or applies it once |

A peer's own refusal (404, 409, 422 and their bodies) is passed through unchanged, with `host` added to the error.

### 7.4 Mutations

Every mutation body carries `idempotency_key` (a ULID the board mints when the control renders and reuses on retry; a second click repeats nothing). A retry resends the same body. The same key with another body is 422 `refused` and writes nothing (section 6.3). Field edits also carry `rev`. Transitions (hold, close, cancel, reopen, answer, decide) do not: as `state.md` principle 5 says, they are guarded by the facts they need, so a stale click is refused by its precondition, and they carry the `rev` the board showed only so a conflict message can say what changed.

**Length caps.** The API takes a card title of at most 1,000 characters, a card body of at most 100,000, a comment of at most 20,000, an answer of at most 20,000, a steer line of at most 20,000 and an ask of at most 8,000. The caps hold for a create, an edit and a forwarded mutation alike. Longer text is 400 `usage` ("title is at most 1000 characters") and writes nothing. A character is a Unicode scalar value, not a byte, and an ask is counted without the space around it. The store checks the caps in the write itself (`tiller_core::limits`), so every writer gets the same refusal. The CLI's `card create`, `card edit`, `ask resolve new`, `ask link new`, `bug file`, `card comment`, a typed `attention answer`, `ask note`, `send --kind steer` and `reply` (a reply is at most 20,000 characters, the comment cap; the board only reads replies) refuse longer text as a usage error (exit 2) with the same message and write nothing. A prompt that `tiller hook` or the transcript tailer records as an ask takes the ask cap: a longer prompt is not recorded, the hook still exits 0, and the observation carries the refusal as `intake_error` (the tailer's as `ask_error`). `tiller import` refuses a bundle whose card title or body runs past its cap, naming the card (exit 5), and writes nothing. An answer cited with `--ask` is the owner's recorded words, so it has no cap.

**Open in terminal.** [H] The focus endpoint is the board's "Open in terminal" button and O key, and `tiller agent focus` runs the same code. It shows the agent's pane to the person at the daemon's own screen, in a `tiller attach` client (6.4), using the terminal app named in the `[attach]` table of `~/.tiller/config.toml` (`terminal-holder.md` 5.3):

```toml
[attach]
terminal = "Ghostty"        # a macOS app name; unset means switch only, and other systems ignore it
# terminal_exec = ["-e"]    # what the app takes before a command to run; "-e" when unset
```

The same table holds `prefix`, the `tiller attach` prefix key (`Ctrl-\` when unset). The holder knows its attach clients (the pane record's `attach_clients`), so the daemon needs no probe with a side effect. Then `opened` says what happened:

| Attach client on this host | `terminal` set | What the daemon does | `opened` |
|---|---|---|---|
| yes | no | `switch` to the pane | `focused` |
| yes | yes | `switch`, then `open -a <terminal>` | `raised` |
| no | yes | `open -na <terminal> --args <terminal_exec> <tiller> attach <session>` | `launched` |
| no | no | nothing here can show it; the board shows the `tiller attach <session>` command to copy | `unseen` |
| either | yes | the app does not open; `problem` says why | `failed` |

`<tiller>` is the daemon's own binary at the stable profile path, resolved to a full path so the app finds it. `[attach]` is re-read whenever `config.toml` changes, so an edit needs no restart (a table that stops parsing keeps the one in use). A `switch` the holder refuses is 503 `unavailable` and nothing else happens; `failed` is a 200. One open runs at a time, so a second click while a client starts waits for it and then raises the app. `[attach] terminal` drives macOS `open`, so a daemon on another system ignores it with a warning in its log. For an agent on a paired peer, the command in the terminal app is `ssh -t <alias> tiller attach <session>`, where `<alias>` is the peer's `peers.<label>.ssh`; no new protocol is needed. A daemon with no screen of its own (a server) has no attach client and no terminal configured, so every focus answers `unseen`. Before the cutover this is "Open in herdr": `herdr agent focus`, the `[herdr]` table and herdr's title probe. **Terminal mirror.** [H] The board shows an agent's live pane and lets the owner type into it. The holder owns the pane (`terminal-holder.md` section 2). The board is one more client of it, beside any `tiller attach` client, and every client sees the same output. Unless the owner asks for a Fit, the board never resizes the pane, so the pane keeps the size its other clients gave it.

- **Guards.** All seven endpoints, the prompt's two included, run every mutation check in 7.1: the owner cookie, the `Host` (loopback, or an `--allow-host` name from its `https://` origin), `Origin`, `Sec-Fetch-Site` and the JSON content type. None writes a record or an event.
- **Stream.** Each open subscribes to the pane in the holder with `sync: "buffer"`. The body is NDJSON (`application/x-ndjson`, `no-store`), one line each: `size` (`cols`, `rows`), the PTY's size, first and again after each `resized`; then `frame` (`seq`, `full`, `bytes`, base64 terminal output). The first frame after a `size` has `full: true` and is the holder's repaint: it draws the current screen on an empty terminal of that size (`terminal-holder.md` 3.4). The frames after it have `full: false` and carry the PTY's own bytes as the agent wrote them, less the terminal queries, which the holder answers itself (`terminal-holder.md` 2.7). A synchronized frame (mode 2026) comes as one `frame`. `closed` (`reason`, with the exit code) ends the body when the agent exits; a pane that has already exited sends its last screen, then `closed`. `unavailable` (`message`) ends it when the holder stops answering. When the holder cuts a subscriber that fell behind (`lagged`), the daemon subscribes again and sends a new `size` and a full frame. `unfit` (`message`) says the stream shows the pane at its own size in place of the Fit it asked for (Fit, below); the stream goes on.
- **Fit.** Until H11, a Fit is single-viewer: one open stream at a time holds the Fit on a pane. An open with `fit` takes the pane's Fit, notes the PTY's size from before it, and resizes the pane in the holder to the board's columns and rows with the holder's `resize`. The body starts with `size` at the board's size, once the holder has resized; a pane already at that size is not resized. A board that changes size sends the new one to `.../terminal/fit`, and the daemon resizes the pane again. When the viewer leaves, the stream ends or the daemon stops, the daemon gives the pane back the size it had before the Fit. A client that resizes the pane during the Fit wins: the Fit sets no size again until the board's next one, and the daemon reads the pane's size from the holder before each resize and when the view ends, so the other client's size is the one given back, and a pane still at it is left alone. Every resize the daemon makes reopens each open view on the pane, so a view without a Fit shows the new size too. A second stream that asks for a Fit on the same pane waits up to 8 s for the first to end, and then gets `unfit` and the pane at its own size; a resize the holder refuses gets `unfit` as well, and the pane keeps its size. Nothing is kept on disk, so a daemon that dies mid-Fit leaves the pane at the board's size until a client resizes it. H11 makes the Fit a size lease on the stream's own subscription (`terminal-holder.md` 2.6), shared by every viewer: the top lease sets the PTY size, a `tiller attach` client that types moves its own lease back to the top, and a lease ends with its connection, so nothing is given back by hand. The board asks for a Fit only from the Agents view's stage, and only while the page is on screen and the stage is not expanded (full screen keeps the Fit and refits to the screen). A holder pane always fits, with no switch, on a phone too, where the typing sheet keeps the stage's size. While a new size is on its way the stage shows the old grid at the chosen font, clipped, and never scales the text down to it. A herdr pane fits only on a computer, on the owner's switch, since its Fit changes herdr's own window; with it off the stage pans or scales the pane as before.
- **History.** The stream starts at the current screen, so rows that scrolled off before it opened never reach the board. `.../terminal/history` reads them with one `screen {read: {recent: lines}, format: ansi}`: the pane's last `lines` rows (at most 1000 for the API; the holder keeps 10,000), wrapped at the pane's width, oldest first and the screen itself last, colors kept as ANSI escapes and rows split by `\n`. It holds no view. The board reads it when the owner scrolls up on the stage or presses History, shows it read-only over the live screen at the same size, and drops it on Back to live or Esc; it never splices it into the live screen, so a later read is always the whole of it again.
- **Tail.** `.../terminal/tail` reads a local pane's visible screen and size once, with `screen {read: visible, format: ansi}`, and answers one row per line split by `\n`, colors kept. It never sends keys and holds no view; at most 4 run at once, and a fifth is 503 `unavailable` until one finishes. Saved herdr machines go at the cutover (section 9), so no agent needs a tail in place of a stream: the board streams every local pane, and a peer's pane is relayed (10.7). A peer agent's tail is a `query` on the peer link (Agent verbs on a peer, below).
- **Bounds.** At most 8 views are open at once. Each view's lines wait in a queue of 64: a browser that falls behind it has its stream ended, never buffered, and opens again for a fresh repaint. A view's subscription ends when its viewer leaves (the request is dropped), when the stream ends, and when the daemon stops, and a Fit it held gives the pane back its size. The holder bounds each subscriber's own queue at 4 MiB (`terminal-holder.md` 2.7).
- **Input.** One request carries keys or a paste, never both. Input is limited to 20 requests a second across the daemon, with a burst of 40; past it the request is 503 and nothing is sent, and the board sends it again in a moment. A key is a name from Tiller's key list (`terminal-holder.md` 4.3), with the spelling the board sends today, and the holder encodes it for the app's current keyboard mode; any other name is 400. A paste goes through the holder's `paste`, inside bracketed paste when the app turned mode 2004 on.
- **Prompt.** When an agent's hook says it waits on a permission prompt (`waiting_permission`), or the holder's screen verdict sees it blocked on a dialog no hook asked for (`waiting_input`, 4.5), the board reads `.../prompt` once and draws the dialog's options as buttons under the stage; a tap sends `.../prompt/answer`, which presses the option's digit alone (Claude Code takes it without Enter), or, for a known cursor menu, the arrow keys from the cursor's row to the option's row and then Enter, in one `keys` request. Nothing polls: the board reads again only for a new wait and after a refused tap, and a read that finds no dialog is tried twice more, one and three seconds later, since the hook can beat the dialog's draw. A wait is named by the `activity_observed_at` the agent began it at: a later observation of the same wait, such as the screen verdict seeing the dialog after the hook did, keeps it, and one after an answer was sent is the next wait. The daemon reads the screen only while the session row says it waits, so a prompt read costs one `screen` read and the stream is untouched. The parser reads Claude Code's current dialog only, the rows from the last full-width `─` rule to the `Esc to cancel` footer on the screen's bottom row, and only when its title is one Claude Code gives the dialog of the tool the session's newest `PermissionRequest` names (or, with none, its newest observation that names a tool): `Bash command` for Bash, `Edit file` for Edit, `Create file`, `Overwrite file` or `Write file` for Write, `Edit notebook` for NotebookEdit, `Fetch` for WebFetch and `Tool use` for an MCP tool. Any other layout is `no_dialog`, never a guess. A dialog no hook asks for, such as Claude Code's folder trust dialog, leaves the session `waiting_input` (the screen verdict sees it blocked), and while the session row says so the parser reads only the known cursor menus, layouts with no digits where the `❯` cursor moves with the arrow keys and Enter picks its row. Each known layout has a fixture test from a real screen. The one known layout is `trust`: the rows from the last full-width `─` rule to the `Enter to confirm · Esc to cancel` footer on the screen's bottom row, titled `Accessing workspace:`, with the folder on the row after the blank one under the title, a `Quick safety check:` question, and exactly two menu rows above the blank row over the footer, `No, exit` then `Yes, I trust this folder`, one of them under the cursor. Its `tool` is empty, `folder` is the folder and `options` number the rows 1 and 2 from the top. A permission wait never reads a cursor menu, and a `waiting_input` wait never reads a permission dialog. `screen` hashes those rows with the selection cursor left out, so a redraw outside the dialog, or a resize that leaves it whole, does not change it. An answer reads the screen again, parses it again and types nothing unless the tool still matches and the hash is the one the buttons were drawn from: otherwise 409 `screen_changed`, and the board reads the new dialog and asks for a fresh tap. The check and the key are two holder requests, so a dialog that replaced this one in the moment between them gets the digit: the hash narrows the window to one round trip, it does not close it. With the Fit on, the strip borrows its height from the stage and the pane keeps its size, since a resize redraws the dialog. On the Agents page a digit key with no field focused taps the button that shows it, as typing it into the dialog would; a cursor menu's buttons show no digit, so no key taps them. Reads and answers spend the same input rate as keys. A tap is the owner's answer, typed for the owner, so it is not an agent answering a prompt (`authority.md` G29); it writes no record or event.
- **Peers.** Saved machines are gone, so every agent runs on this host or on a paired peer. An agent on a paired peer host is watched and typed into from the board host: the stream and history are relayed from the owning host, and input and the Fit go to it as signed frames on the same pane link (10.7). Its tail and its prompt read are queries on the peer link, and its answer and the other agent verbs are forwarded mutations (D20; Agent verbs on a peer, below).

**Forwarding** (ADR 0003). Every mutation body above may carry `host` (a peer label; absent means this host). With a peer `host`, the daemon checks the cookie and headers as for any mutation, refuses at once with 503 `peer_unreachable` when the link is not `live`, and otherwise sends the body as a signed `mutate` frame (section 10.3) and returns the peer's response with `host` added. Project slugs are unique only per host and `fleet` exists on every host, so `POST /api/v1/cards` takes `host` like the rest; the new-card picker sends the host of the project the owner chose. The forwarding allowlist is exactly: `POST /api/v1/cards`, `PATCH /api/v1/cards/{id}`, `POST .../comment`, `POST` and `DELETE .../hold`, `POST .../close`, `.../cancel` and `.../reopen`, `POST` and `DELETE .../deps`, `POST /api/v1/attention/{id}/answer`, `POST /api/v1/approvals/{id}/decide`, `POST /api/v1/projects/{id}/asks`, `POST /api/v1/projects/{id}/orchestrator`, `POST /api/v1/agents/restart-stale`, and since D20 (Friday 2026-11-13) `POST /api/v1/attention/{id}/withdraw` and the agent verbs `POST /api/v1/agents/{session}/interrupt`, `.../steer`, `.../stop`, `.../pause`, `.../unpause`, `.../resume` and `.../relaunch`, and `POST /api/v1/agents/{session}/prompt/answer`. The asks and the start let the board's Ask dialog reach a peer's project: the ask is the owner's note, never an agent's, and the start is the peer's own `tiller orchestrator start`, so the peer must have its spawn tools configured (else the peer's refusal comes back with `host`). The agent verbs run on the peer as the same core functions the peer's own board runs, as `board@<label>` with `via_peer`, with the peer's own preconditions, holder and proof (Agent verbs on a peer, below). Not forwarded: `config`, because a setting is a path on the host that owns it, so the board shows a peer's missing settings as that host's own with the command to run there; `memory/proposals/decide`, `memory/edits`, `memory/changes/{proposal}/undo`, `memory/proposals/{id}/repropose` and `memory/proposals/{id}/eval`, because memory reads stay local (7.3), so the board host never shows what a decision would keep; `projects` (a project add) and `peers` (a pairing), `PATCH projects/{id}` (a project edit), `projects/{id}/stage`, `projects/{id}/delete` and `projects/{id}/retire`, because the forwarded owner has no project commands (`authority.md` section 3); `projects/{id}/grants` and `grants/{id}`, because a grant lets work merge without the owner, so it is made and revoked only on the host that holds it; `bug-project`, because each host picks its own bug project and the board's Move of a Tiller bug is a `POST /api/v1/cards` to the target host, then a close `superseded` on the card's own host, each forwarded as it needs; and `agents/{session}/focus`, which opens a peer's agent in the terminal app with `ssh -t <alias> tiller attach <session>` (7.4, Open in terminal) [H]; `agents/{session}/terminal`, `.../terminal/history` are not mutations, and are relayed over a pane link, and `.../terminal/input` and `.../terminal/fit` go as signed frames on that link, not as `mutate` (10.7); `.../terminal/tail` and `.../prompt` are reads, sent as a `query` on the peer link (10.2); `interventions/{id}/label`, because the Health numbers are this host's own; `replies/{id}/read`, because a reply is read on the host that holds it, as its replies are never federated (7.3), so the board never marks a peer's reply it could not list; and `pollers/{source}/run`, because each host runs its own pollers. A mutation off the list with a peer `host` is 502 `peer_refused`.

| Prompt answer | `.../prompt/answer` | forwarded `mutate` (10.3) | `mutate` op `agents/{session}/prompt/answer` | the Inbox answers with no stream open; the key makes a retry replay `sent` and never type twice; the peer checks its own screen just before it types |
| Interrupt | `.../interrupt` | forwarded `mutate` | `mutate` op `agents/{session}/interrupt` | it records `interrupt_sent`, its key binds the press, and it waits for proof |
| Steer | `.../steer` | forwarded `mutate` | `mutate` op `agents/{session}/steer` | it writes an outbox row that the peer types when the pane is idle |
| Stop | `.../stop` | forwarded `mutate` | `mutate` op `agents/{session}/stop` | it ends a session row and cleans a run after a proof |
| Pause, unpause | `.../pause`, `.../unpause` | forwarded `mutate` | `mutate` op `agents/{session}/pause` or `.../unpause` | record writes on the run |
| Resume, relaunch | `.../resume`, `.../relaunch` | forwarded `mutate` | `mutate` op `agents/{session}/resume` or `.../relaunch` | they start a session on the peer's own holder after proof, and the key keeps a retry from starting one twice |
| Withdraw an attention item | `attention/{id}/withdraw` | forwarded `mutate` | `mutate` op `attention/{id}/withdraw` | a record write on the host that holds the item |
| Open in terminal | `.../focus` | not forwarded | none | it stays `ssh -t <alias> tiller attach <session>` on this machine (Open in terminal, above) |

- **The rule.** A verb that writes a record, sends keys outside a stream, is keyed or waits for proof is a forwarded `mutate`: the `peer serve` link is always open, so the verb needs no stream, and the peer's idempotency table makes a retry safe (10.3 step 4). A one-shot read is a `query` on the same link. Only the keys and the Fit the owner types on a stream ride its pane link, where they keep their order (10.7 step 7).
- **Scope.** Every verb needs the `act` scope, except a watch, a history read and a tail, which a `read` pairing may make, as it may watch (10.7 step 4). The prompt read needs `act` too: it serves only the answer, and it spends the peer's input rate. This host checks the scope before a frame goes out (502 `peer_refused`, `reason` `read_scope`), and the peer checks it again on its key row.
- **Proof waits.** Interrupt, stop, resume, relaunch and the answer wait on the peer for their proof. For these five the board host waits up to a proposed 60 s for the `result`, not 10 s (10.3 step 6). Past it the answer is 504 `forward_uncertain`, and a retry with the same key gets the peer's stored answer and acts nothing twice.
- **Errors.** As for any forwarded call: 503 `peer_unreachable` when the link is not `live`, 502 `peer_refused` with the peer's `reason` (10.3 step 3), 504 `forward_uncertain`. The peer's own refusals pass back with `host`: 422 `refused` (an agent not working, an active run, a draft or a dialog, an ended run), 409 `screen_changed` for an answer, 400 for an option the dialog does not offer, 404 for an unknown session, 503 `unavailable` when the peer's holder is unreachable or past its input rate.
- **Actor.** Each runs on the peer through the same core function its own board runs, as `board@<label>` with `via_peer`, as every forwarded mutation does. Restart stale keeps its own rule (the peer's own board, above). A tap is the owner's answer typed for the owner on the peer too (`authority.md` G29).
- **No third host.** The peer runs each verb on its own sessions only; `peer serve` and `peer pane` have no client half (`authority.md` G42).

### 7.5 SSE stream

One stream: `GET /api/v1/events` (`text/event-stream`).

```
id: 4182
event: change
data: {"seq":4182,"at":"2026-11-02T14:05:09.123Z","kind":"attention.answered","txn":"attention.answer","entity":"attention","entity_id":"01JC...","rev_after":3,"card_id":"01JC...","entity_state":{...},"card":{...}}
```

- **Fields.** `seq` (also the SSE `id`), `kind`, `txn`, `entity`, `entity_id`, `rev_after` (null for append-only entities), `card_id`, `entity_state` (the entity's API shape when the event is sent, with its current `rev`, so the client can `setQueryData` without a fetch; a later write may already be included, and the client keeps whichever `rev` is higher; null when the daemon could not read the entity or the entity has no API shape of its own, and then the client fetches the read the entity belongs to) and, when `card_id` is set, `card` (the card's recomputed `card_column` row, since a column is derived and any of the card's facts can move it).
- **Order.** One SSE message per `events` row, in `seq` order. A mutation that writes several events sends them consecutively; the client applies each and ignores any whose `rev_after` is older than what it holds.
- **Source.** The daemon reads new `events` rows (it sees CLI and hook writes through `data_version` polling) and sends them. Every pushed change is an `events` row, so every change can be resumed. Cache refreshes write `pane.changed`, `host.changed`, `worktree.changed` and `quota.changed` events only on a change (`state.md`, `cache.refresh`), and observations write `observation.recorded` only when a session's verdict changes. An edit made in the memory repo outside Tiller (an editor's save, a pull, a commit by hand) moves no row, so the daemon's memory watcher writes one `memory_repo.changed` event for it (`memory.md` section 12, `mem.outside_edit`), and the board reads the memory view again. The watcher stats the repo once a second and starts no process while it is still. It waits for a burst of writes to end, reads the repo under the repo lock, and writes nothing for Tiller's own commit, whose events already refresh the board. A document changed within two seconds of a read is read again on each poll until it is older, since a coarse file clock can leave a same-length rewrite with the stat it had. A missing repo is quiet. The watcher keeps its last look in the store (`meta.memory_watch`), so a daemon that starts again compares its first look with it, and an edit made while the daemon was down is one change on start; with nothing kept, the first look is the baseline. Tests: `cli::memory_watch::an_edit_made_outside_the_board_reaches_the_stream`, `daemon::memory::watch::tests::an_edit_made_while_the_daemon_is_down_is_seen_on_start`, `daemon::memory::watch::tests::a_rewrite_that_leaves_the_stat_as_it_was_is_still_a_change`.
- **Resume.** The browser's `EventSource` sends `Last-Event-ID`. The daemon replays every row with `seq` greater than it, then streams live. If the gap is more than 5,000 rows, or the id is greater than the newest `seq` (a restored database), the daemon sends `event: reset` with `{"seq": <newest>}` and the client refetches the snapshot silently while the UI stays put. It also marks every other read stale (an open card, its timeline, memory, Settings, Health), so the ones on screen fetch again, and it keeps its old cursor until a snapshot lands: a failed fetch is tried again with a growing wait, and a stream that drops meanwhile resumes after the old cursor, so the daemon sends `reset` again. Because events are durable, this works across a daemon restart (T2.8 acceptance).
- **Keepalive.** A comment line every 15 s, and `retry: 1000`.
- **Cap.** One session holds at most 64 open streams: at an `--allow-host` name a session is its owner cookie, and all of loopback is one session. A board tab holds one stream, so an owner never comes near the cap. Past it the request is 429 `too_many_streams`, and a stream gives its place back when it ends. A stopping daemon or a sign-out ends a stream even while the browser has stopped reading it.
- **Peers** (section 10.2). A peer's change is sent as `event: peer` with `data: {"host","host_id","as_of","change":{<the change shape above>}}` and no SSE `id`, since a peer's `seq` is not this host's. A link state change is `event: link` with `{"host","link","as_of","stale_reason"}`. When the browser reconnects, the daemon sends `event: peer_reset` per peer, with the peer's current cached `queries`, after replaying this host's rows, so a peer's changes missed during the gap are never needed.
- **Time.** Staleness is derived from age, so it changes without an event. Each snapshot and each `reset` carries `server_time`; the client computes staleness from `activity_observed_at` with the clock offset, using the thresholds the snapshot carries.

### 7.6 Boot snapshot

The daemon renders `index.html` with the snapshot inlined:

```html
<script type="application/json" id="tiller-boot">{"v":1,"server_time":"...","last_event_seq":4181,"thresholds":{...},"queries":{"/api/v1/board?filter=all":{...},"/api/v1/attention?state=open":{...},"/api/v1/agents":{...},"/api/v1/machines":{...},"/api/v1/quota":{...},"/api/v1/projects":{...}}}</script>
```

- **Peers** (section 10). The snapshot adds `"peers":[{"host","host_id","link","as_of","server_time_offset_ms","scope","last_event_seq"}]`, and every federated query entry already includes the peer rows the daemon held when it rendered.
- Each `queries` entry is exactly the response of that GET, built by the same handler, keyed by its path and query string. The board's query option factories (T3.1) map those paths to query keys, so the snapshot never drifts from the API.

## 8. Quota feed

- **Run.** Every 5 minutes the daemon runs `quota-axi --provider <p> --full --json` for each provider in the config value `quota_providers` (default `claude`; other providers matter only once another harness has an adapter, section 10), with a 60 s timeout, one at a time (a run still going when the next is due is skipped, never overlapped). `StopFailure:rate_limit` and `Notification:quota_auto_resume_fired` trigger one early run, at most once a minute. It is a script; it costs no model tokens.
- **Parse by allowlist.** The output is deserialized into a struct that has only these fields: `schemaVersion`, `generatedAt`, and per provider `provider`, `state.status`, `state.refreshedAt`, and per window `id`, `label`, `kind`, `windowSeconds`, `percentRemaining`, `resetsAt`, `pace.status`, `pace.reservePercentPoints`, `pace.burnMultiple`, `pace.elapsedPercent`, `pace.projectedExhaustedAt`. The `account` and `accountKeys` blocks, `attempts`, `source` and every other field are never deserialized, so an account id or email cannot be stored, logged or sent even if quota-axi renames a field. Raw stdout is never logged.
- **One account per provider.** quota-axi reports the one credential it selected for each provider [T: one Claude entry on host B]. If it ever returns several entries for one provider, the feed keeps the first and records `fetch_error = multiple_accounts`; it never tells them apart by account.
- **Store.** One `quota_windows` row per window, in one `cache.refresh` transaction: `label` = `<provider>:<window id>` (for example `claude:seven_day`), `title` = the window's `label`, `kind` = its `kind` (`weekly`, `model`, `credits`, ...), and `percent_remaining`, `resets_at`, `pace`, `reserve`, `burn_multiple`, `elapsed_percent`, `projected_exhaustion_at` from the fields above. A failed run keeps the previous rows and sets `fetch_error` (a short code, never quota-axi's stderr) and leaves `fetched_at` as it was.
- **Expose.** `GET /api/v1/quota` and `tiller quota` return each window with `title`, `percent_remaining`, `resets_at` (and Lisbon text with the weekday), `pace`, `reserve`, `burn_multiple`, `elapsed_percent`, `projected_exhaustion_at`, `fetched_at`, `stale` (older than 15 minutes) and a `dot`:

  The dot reads the provider's window with `kind = weekly`. `pace` values seen [T]: `ahead`, `behind`, `unknown`; any other value counts as not ahead.

  | Dot | When (on the weekly window) |
  |---|---|
  | `red` | `percent_remaining` at or under the weekly floor (3%, AGENTS.md rule 8); a projected exhaustion before `resets_at` alone is not red |
  | `amber` | `pace = ahead` |
  | `green` | otherwise |
  | `grey` | stale or never fetched; the tooltip says since when |

- **Dispatch.** `tiller quota [--size S|M|L]` (default `M`) adds `dispatch` to each fresh weekly window: `decision` (`go` or `hold`) and `note` (one line, or null). It holds only when `percent_remaining` is under 10, or when `projected_exhaustion_at` comes before now plus the size's work estimate (S 2 h, M 6 h, L 12 h wall-clock; no per-run cost record exists, so the card size stands in). A window ahead of pace that would last through the work is `go` with a note saying so, which the orchestrator carries in its note to the owner. The rule is `tiller_core::quota_rule`; the spawn floor below is a separate, lower check and away mode's `quota_floor_percent` is unchanged.

- **Use.** The sidebar footer and Health read it; `tiller spawn` checks it live (P04, T4.2) and fails closed when it is stale (point 35). The per-account floor and the share per host are config owned by T4.2; the feed carries no account id, so the share is configured per host.

- **A refused start reaches the inbox.** When the quota floor refuses a `tiller spawn` or `--promote`, the card is held until the latest reset among the weekly windows that are under the standing floor (`hold.set`, reason "the weekly quota is under the floor"), and one `decision` attention item opens with the options "Start now anyway" and "Wait for the reset". A refusal that an active away contract's `quota_floor_percent` would still give past the standing floor is a plain refusal: no hold and no item, because no answer can lift that floor. A card that already has a hold for another reason keeps that hold, and the item still opens. A second refusal for the same card opens no second item. "Wait for the reset" keeps the hold, and while that quota hold stands a refusal asks nothing new. When the hold's date passes, the dated-hold release asks again, and it withdraws the old item first, so one item stays open. "Start now anyway" is applied when the owner or the board answers: it releases the quota hold (never a hold for another reason), and the orchestrator may then run `tiller spawn <card> --past-quota-floor` (with `--promote` for a scout), which starts that one run past the floor and records the answered item in the `run.started` payload (`checks.quota_override`). Only the newest answered quota item for the card and role counts, and any later `run.started` of that role on the card uses it up, so one answer starts at most one run. The orchestrator cannot answer the item. Only the standing floor is skipped: an away contract's `quota_floor_percent`, capacity, the model rules and the RAM and disk floors still apply.

### 10.1 Pairing

`tiller peer add <label> --ssh <alias> [--read-only]` on the board host, run by the owner in a terminal:

1. Refuses a session caller (`authority.md` G22), an alias that starts with `-` or holds a character other than letters, digits, `.`, `_`, `@`, `:` and `-`, and a label still paired to a different peer (`tiller peer remove` it first).
2. Generates an Ed25519 key pair. The private half goes to `~/.tiller/peers/<label>.key` (mode 0600, written atomically), never to `state.db` or a log.
3. Runs `ssh -t <alias> tiller peer accept --from <this label> --viewer-host-id <this meta.host_id> --pubkey <public half> --scope act|read`. `-t` gives the peer a terminal, so the peer sees its owner principal (`authority.md` section 3) and asks for confirmation; it refuses when its config has `federation.accept = false`. It writes `peer_keys` and prints its `host_id`, label and versions.
4. Commits `peer.pair` here (`hosts` row with `peer_scope` and `peer_host_id`) and config `peers.<label>.ssh`, then the daemon opens the link. A failure at step 3 deletes the key file; nothing else was written. A failure at step 4 also deletes the key file, which leaves the peer's new `peer_keys` row with no private half; running `tiller peer add` again replaces it, since a new accept from the same board host revokes the old row.

**From the board.** Settings, Hosts, Add a host sends `POST /api/v1/peers` (7.4) with the label, the alias and the scope. The board credential stands in for the terminal (`authority.md` G45), and the daemon runs the same four steps with the same code, one pairing at a time:

1. Refuses what step 1 refuses, plus this host's own label and any label already paired (422 `label_taken`): the owner Unpairs that host first from its Settings > Hosts card, and re-pairing a label in place stays `tiller peer add` in a terminal. It also refuses an alias that config `peers.<other>.ssh` names for a paired label (422 `already_paired`), and a `config.toml` that does not parse (503), so step 4 cannot fail on it after the new host accepted.
2. Writes the private half to `~/.tiller/peers/.<label>.board.key.pending` (mode 0600, atomic) until the new host accepts. The name is its own, so a `tiller peer add` of the same label never shares it.
3. Runs `ssh -T -o BatchMode=yes -o ConnectTimeout=10 -- <alias> tiller peer accept --from <this label> --viewer-host-id <this meta.host_id> --pubkey <public half> --scope act|read --unattended --json`, 30 s in all. Batch mode and ssh's default host key check, as the link dials (10.2): an unknown host key fails and never asks. With no terminal there is no prompt, so `--unattended` replaces the terminal check with `peer serve`'s start check (sshd for the owner: `SSH_CONNECTION` set, no `TILLER_SESSION_ID`, no `CLAUDECODE`, no Claude Code process among its ancestors). `federation.accept = false` refuses it as it refuses the terminal accept. The `peer.accepted` event there has actor `board@<this label>` and `unattended: true`. The answer is the last line of the output that parses as a JSON object. An answer whose `host_id` is already paired here under another label is 422 `already_paired`: that host now holds the new key in place of the other label's, and `tiller peer add <other>` restores that link.
4. Renames the key into place, writes config `peers.<label>.ssh`, then commits `peer.pair` and its `config.changed` as `board`. The supervisor opens the link within its next pass (2 s), and `host.changed` puts the new host in the list at once: until that pass, `machines` shows it as a peer with `link` `never`.

Every failure at step 3 deletes the pending key, and a failure at step 4 deletes the key file, as the command's undo does. The answer never carries the private half, only its fingerprint.

Adding a host stays one command, or one form. A peer whose database was replaced reports a new `host_id` and is `refused`; `tiller peer remove <label>` then `tiller peer add` pairs it again. Removing one is `tiller peer remove <label>` here, or Unpair in its Settings > Hosts card, and, to make the old key useless at once, `tiller peer revoke <label>` there, or Revoke key in that host's Boards that reach this host. Each side cuts the end it owns, and neither is forwarded.

### 10.2 Peer link, freshness and resume

One SSH session per paired peer, opened by the board host's daemon: `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=2 <alias> tiller peer serve --from <label>`. Frames are JSON lines, protocol `tiller-peer/1`:

| Frame | Direction | Carries |
|---|---|---|
| `hello` | board host to peer | `v`, `from`, `key_id`, `viewer_host_id`, `nonce`, `ts`, `sig` (Ed25519 over all of them and the peer's expected `host_id`), `last_seq` (the peer `seq` the board host last applied, or null) |
| `welcome` / `refused` | peer | `host_id`, `label`, `schema_version`, `tiller_version`, `server_time`; or `reason` (`revoked`, `unknown_key`, `bad_sig`, `clock_skew`, `replayed`, `version`, `accept_off`) |
| `snapshot` | peer | `server_time`, `last_event_seq`, and `queries`: the peer's own `board?filter=all` (its `asked` rows without `summary`: ask text stays on the peer), `attention?state=open`, `agents`, `projects` and its local `machines` row, built by the same handlers as 7.6, in one read transaction |
| `event` | peer | one `events` row in the SSE change shape (7.5), in `seq` order |
| `beat` | peer | `server_time`, `last_event_seq`, every 10 s |
| `refresh` | board host | nothing: asks for a fresh `snapshot` (Fresh, below) |
| `query` / `result` | board host / peer | `id`, an allowlisted single-entity GET (`cards/{id}`, `cards/{id}/timeline`, `runs/{id}`), one of an agent's two screen reads (`agents/{session}/terminal/tail`, and `agents/{session}/prompt`, which needs the `act` scope; D20, 7.4 Agent verbs on a peer) or `doctor` (the peer's `tiller peer serve` runs the checks of `GET /api/v1/doctor` in its own SSH session environment, off the link's thread so beats and other queries keep flowing, one run at a time per link: a `doctor` query that comes while one runs gets the answer of that run; it writes nothing); `id`, `http_status`, `body` |
| `mutate` / `result` | board host / peer | section 10.3 |
| `pane_open` | board host to peer, on a pane link | section 10.7 |
| `pane_input` / `pane_fit` / `result` | board host / peer, on a pane link after a `stream` open | section 10.7 |

- **Hello checks.** The peer answers `hello` only when config `federation.accept` is not `false`, the key row is unrevoked, the signature is valid, `ts` is within 120 s of its clock and the `nonce` is new; otherwise `refused` with `accept_off`, `revoked` or `unknown_key`, `bad_sig`, `clock_skew` or `replayed`. The nonce check comes last, so only a hello that passed the others is kept. Each `peer serve` is its own process, so the peer keeps the nonces it took in the file `peer-nonces` under its home, read and written under a lock: each until its `ts` plus 120 s, when the freshness check would refuse it anyway, and at most 4,096, past which the one that expires first goes. A file that cannot be read or written ends the link with no `refused`, and the board host backs off. It re-reads `federation.accept` and the key row on every `mutate` and `query`, and closes the link when either changes, so setting `federation.accept = false` cuts a live link at once.
- **Fetch.** After `welcome`, the peer sends `snapshot` when `last_seq` is null, older than 5,000 rows, or greater than its newest `seq` (a restored database); otherwise it replays every row after `last_seq`. Then it streams `event` frames as it sees new rows (`data_version` polling every 200 ms, like the daemon) and a `beat` every 10 s.
- **Fresh.** The board host applies each `event` to its in-memory copy at once and pushes it to browsers as `event: peer`. Derived columns are re-read: while events arrive, it asks for a fresh `snapshot` at most once every 2 s (coalesced), so a column a peer derives never drifts from the peer.
- **Link state.** `live`: a frame within the last 25 s. `lagging`: the last frame 25 s to 2 min ago. `down`: no frame for 2 min, or reconnect failing. `refused`: the last `hello` was refused, or the peer's `host_id` differs from `hosts.peer_host_id`. `never`: no `welcome` yet. Every change is an `event: link` and a `host.changed` event here.
- **Reconnect.** When the SSH child exits, the connection is refused, or the link reaches `down` (no frame for 2 min, which also catches a frozen `peer serve` behind a live TCP session), the daemon kills the SSH child and retries after 5 s, 15 s, 30 s, then every 60 s. `clock_skew` and `version` refusals retry every 60 s. Any other `refused` (such as `accept_off` or `revoked`) stays `refused` and retries slowly, after 5, 10 and 20 minutes, then every 30 minutes, so a link comes back on its own once the peer's owner clears the cause, and a revoked key never hammers the peer. The backoff starts over after a link that was welcomed is lost. Pairing again (`tiller peer add`) starts a new link at once.
- **Clock.** Each `welcome` and `beat` carries the peer's `server_time`; the board host keeps the offset and serves it in `peers[].server_time_offset_ms`, so a peer agent's activity staleness is computed against the peer's clock, not this one.
- **Isolation.** Each link runs in its own task with its own timeouts. Nothing on this host waits on it: no local write, no SSE push of a local event, no poller.

### 10.3 Forwarded mutations

1. The board sends a 7.4 mutation with `host = <peer label>`. This daemon checks the cookie and headers (7.1), that the link is `live` (else 503 `peer_unreachable`), that the pairing is `act` (else 502 `peer_refused`) and that the op is on the allowlist (7.4).
2. It sends `mutate{id, op, target, body, idempotency_key, ts, viewer_host_id, peer_host_id, key_id, sig}`. `op` names the 7.4 endpoint. The signature covers every other field.
3. The peer's `peer serve` verifies, in this order, which is the one canonical order (`authority.md` section 7 and G41 refer to it): config `federation.accept` is not `false`; the key row exists and is unrevoked; the signature; `ts` within 120 s of its clock; `peer_host_id` is its own; the row's scope is `act`; `op` is allowlisted; the owner marker (`authority.md` G26) still names `tiller`; and the target is in a project this host owns (G25). A failure is `result{http_status: 502, code: "peer_refused", reason}` and writes nothing.
4. It then runs the same core function its own board would run (protocol principle 1), with every precondition, `rev` and `head_sha` check of its own, with `actor = board@<viewer label>` and `via_peer` in the event payload. Its `idempotency_key` table makes a repeat return the stored response. The key is bound to its request as a local board key is (section 6.3): the peer records the SHA-256 of the frame's `op`, `target` and `body` (object keys sorted, the top-level `rev` left out). A retry with the same key and the same request replays. The same key with another body or target is the peer's 422 `refused` and writes nothing.
5. Its response comes back as `result`, and the board host returns it to the browser with `host` added. The peer's own SSE and its `event` frame carry the change, so the board updates the same way it does for a local write.
6. No result within 10 s is 504 `forward_uncertain` (60 s for the agent verbs that wait for proof: 7.4, Agent verbs on a peer). The board shows "sent, not confirmed" and keeps the control's `idempotency_key`. Neither daemon holds or replays anything. When the link is `live` again the owner may retry from the control; the board host signs a new frame with a fresh `ts` and the same key, and the peer either returns the stored response or applies it once.

The peer never forwards a frame on. A board host that is also some other host's peer serves only its own records over its own link.

### 10.4 An unreachable peer

- The board host keeps working. Its own cards, agents and mutations do not wait on any link (10.2, Isolation).
- The peer keeps working. Its orchestrators, workers, delivery, landing and its own localhost board need nothing from the board host.
- The board host keeps the last snapshot and events it applied, in memory. A daemon restart drops them, and the peer's cards reappear when the link is `live` again.
- A mutation for the peer is refused at once with 503 `peer_unreachable` and nothing is queued (ADR 0003, owner choice 3). The board says so on the control; the owner retries when the link is back.
- No attention item is opened for a link: an outage is not a question for the owner. `GET /api/v1/health` lists each link's last success and last error; the Machines row shows the state; the existing 24 h Safety signal (`recovery.md` R05) still applies to a peer that stays down.

### 10.5 Staleness on the board

- Every card, attention item and agent from a peer carries a host chip with the peer's label. Local rows carry one too when any peer is paired.
- While the link is `live`, a peer's rows look like local rows.
- Otherwise its rows are dimmed and say "as of <time>" in Europe/Lisbon with the weekday, and the age ("as of Tue 14:02, 6 min ago"). Their controls are disabled, with the reason as the tooltip ("host-b is unreachable since Tue 14:02", "host-b refused the link: key revoked").
- A `read` pairing shows its rows live with controls disabled ("view only pairing").
- The new-card project picker groups projects by owner host and disables a group whose link is not `live`.

### 10.7 Watching and typing into a peer's pane

The board shows a peer host's agent pane and scrollback, and the owner types into it and Fits it to the stage as into a local pane. The board host relays them; the owning host serves its own pane, from its own holder or herdr (`Live::subscribe` and `screen {read: {recent: lines}}`, `terminal-holder.md` section 8), and types through its own input path. A pane link carries only the stream, the history, the owner's keys and the Fit. The tail and the prompt read go as a `query` on the peer link, and the answer, interrupt, steer, stop and the other agent verbs as a forwarded `mutate` (D20; 7.4, Agent verbs on a peer). A pane link takes no other frame, as it takes no `mutate` today.

1. The owner opens the agent's terminal on the board. The browser sends the usual terminal request with the agent's `host`. This daemon checks the cookie and headers (7.1) and that the link is `live` (else 503 `peer_unreachable`), and takes a viewer (at most 8 on this host, 7.4 Bounds).
2. A Fit takes this host's Fit turn for the peer's pane, as a local Fit does (7.4, one viewer at a time). A `read` pairing, or a turn another view holds, opens the stream with no Fit and an `unfit` line first. Tail, prompt and answer do not use the pane link (7.4, Agent verbs on a peer).
3. The daemon opens a pane link: a second SSH session, `ssh -T -o BatchMode=yes <alias> tiller peer pane --from <label>`, with one signed frame, `pane_open{session, kind, lines, fit, ts, viewer_host_id, peer_host_id, key_id, sig}`. `kind` is `stream` or `history`; `fit` is the board's `{cols, rows}` for a `stream`, or absent. The signature covers every other field, `fit` included when it is present.
4. The peer checks `federation.accept`, the key row, the signature, `ts` within 120 s and `peer_host_id` in the order of 10.3 step 3. A `fit` needs the `act` scope (else `read_scope`); watching with no Fit writes nothing, so a `read` pairing may watch. Last, it takes the request's `id` as a nonce in the same set as a `hello` (10.2), so the same signed request again is `replayed`. A failure is one `refused{reason}` frame (`bad_sig`, `unknown_key`, `revoked`, `clock_skew`, `accept_off`, `wrong_host`, `read_scope`, `replayed`) and nothing is streamed; the board host shows it as 502 `peer_refused`. While the stream runs the peer re-reads the key row whenever another connection committed (`PRAGMA data_version`) on every poll (200 ms) and sends no line once that check fails, so a revoke ends it at once, like 10.2 for `peer serve`; it re-reads `federation.accept` every second. A frame that is not `pane_open` gets no answer.
5. The peer then answers with the same NDJSON lines as a local mirror (7.4, Stream, History), or one `result` frame. On a `stream` it applies the Fit, and gives the pane its size back when the stream ends, before `peer pane` exits.
6. The owner types or the stage changes size: the browser sends the usual `.../terminal/input` or `.../terminal/fit` with the agent's `host`. This daemon checks the cookie and headers, that the link is `live` (else 503) and that the pairing is `act` (else 502 `peer_refused` with `read_scope`), and finds this host's open stream of that pane (else 422 `refused`: open the agent's terminal first). It sends `pane_input{id, open_id, seq, session, keys | text, ts, viewer_host_id, peer_host_id, key_id, sig}` or `pane_fit{id, open_id, seq, session, cols, rows, ts, viewer_host_id, peer_host_id, key_id, sig}` on that link's stdin. The signature covers every other field. `open_id` is the `pane_open`'s `id`, and `seq` counts up from 1 on each link, so keys keep the order they were typed in.
7. The peer checks each frame in this order: the key row is unrevoked and is the `pane_open`'s own key; the signature; `ts` within 120 s; `peer_host_id`; the row's scope is `act`; `open_id` and `session` are this link's; `seq` is past the last one taken (else `replayed`). A failure is `result{http_status: 502, code: "peer_refused", reason}` and types nothing. Then the session must be its own and not ended (else 422 `refused`), and input spends an input rate of its own per pane link, 20 a second with a burst of 40 (7.4, Input), not shared with this host's own board yet. It types through its own input path, holder or herdr, as a local key does, or refits the stream's Fit, and answers each frame with one `result` between the stream's lines. The board host returns it to the browser with `host` added.
8. Nothing is dropped without a word. A frame the board host could not write is 503 `peer_unreachable`. A link that ends, or no `result` within 10 s, is 504 `forward_uncertain`, and the keys may have reached the pane.
9. The board host copies the lines to the browser through a queue of 64. A link that ends mid-stream gets a final `unavailable` line, and the board shows that the peer is unreachable and tries again. Closing the browser stream closes the link's stdin: the peer gives back the Fit and ends, and this host's Fit turn is held until it has.

`peer pane` starts only under sshd for the owner, like `peer serve` (`authority.md` G44, G46). The peer's own board and a `peer pane` keep separate Fit turns until the holder's lease (H11), so a Fit on the peer's own board and one from the board host at the same moment can both resize the pane; each gives back the size it found.
